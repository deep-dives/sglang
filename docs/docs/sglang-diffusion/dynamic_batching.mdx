动态批处理是 SGLang-Diffusion 的一种可选服务化模式，它把兼容的排队请求合并成一个原生管线批。它与 LLM 的连续批处理和分词器批处理是两回事。

把它用于相同模型与采样形状下的并发 T2I 或 T2V 流量。对延迟敏感或高度混合的流量，请保持单请求服务。

## 启用

动态批处理默认关闭（`--batching-max-size 1`）。

对于带外部 AR 服务器的 GLM-Image T2I，兼容请求会共享一次批量的 AR `/generate` 调用。DiT 去噪与 VAE 解码仍是每个请求独立执行；GLM-Image 不对 DiT 工作做批处理。

```bash Command
sglang serve \
  --model-path black-forest-labs/FLUX.1-dev \
  --port 30010 \
  --batching-mode dynamic \
  --batching-max-size 8 \
  --batching-delay-ms 5 \
  --enable-batching-metrics
```

请求格式参见 [兼容 OpenAI 的 API](./api/openai_api)。

当某个模型或分辨率需要比 `--batching-max-size` 更低的上限时，用 `--batching-config /path/to/batching_config.json` 加载 JSON 规则：

```json Config
{
  "schema_version": 1,
  "rules": [
    {
      "model_contains": "Qwen-Image",
      "resolution": "1024x1024",
      "max_batch_size": 1
    }
  ]
}
```

T2I 与 T2V 模型动态批处理的最初实现见 [#18764](https://github.com/sgl-project/sglang/pull/18764)。当前兼容矩阵如下，随着覆盖面扩大将持续更新。常用模型 ID 与优化支持情况见 [支持的模型与优化兼容性](./compatibility_matrix)。

<Note>
💡 AI Infra 学习笔记：动态批处理是扩散服务化版的"批处理"——它把多个兼容请求合并成一次原生管线批，用更大矩阵的 GEMM 摊薄 kernel 启动与调度开销，提升吞吐量。但它和 LLM 连续批处理的关键区别是：LLM 的批在每步都可增删请求，而扩散请求是"同模型、同采样形状"才能合并，且合并后的批要么整体成功、要么整体失败，所以它默认关闭、按场景开启。
</Note>

## 备注

- 只有模型输入、采样参数、输出处理以及任何已配置规则都兼容时，请求才会被合并成批。
- 没有启动探测、运行时学习、OOM 重试或自动回退到单请求。如果合并后的批次失败或无法拆分，该批次中的每个请求都会收到错误。
- 批次形状可能改变 kernel，因此单请求与动态批的输出不保证逐位一致。
- 用 `--enable-batching-metrics` 查看实际成批情况：

```text
Dynamic batch dispatch: size=2/8, user_max=8, queue_wait=5.12ms, stop_reason=delay
Dynamic batch dispatch: size=1/8, user_max=8, queue_wait=0.04ms, stop_reason=config_cap:1
Dynamic batch stats (last 5 dispatches): avg_size=2.80, merged_rate=60.0%, full_rate=20.0%, utilization=35.0%, wait_avg=3.21ms, wait_p95=5.12ms, top_rejects=none
```
