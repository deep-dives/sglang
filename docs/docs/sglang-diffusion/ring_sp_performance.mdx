序列并行（sequence parallelism）把长图像或视频的潜空间序列拆分到多块 GPU 上。在 SGLang Diffusion 中，公开的控制项有：

- `--sp-degree`：序列并行总度数
- `--ulysses-degree`：Ulysses 并行度数
- `--ring-degree`：环形并行度数
- `--sp-attention-mode`：每个 SP 组内部使用的注意力交换方式

这些度数必须满足：

```text
sp_degree = ulysses_degree * ring_degree
```

默认的 `--sp-attention-mode ulysses` 使用 all-to-all 把序列分片重新分布到注意力头上。`--sp-attention-mode kv_gather` 保持查询按序列分片，对键和值做 all-gather，然后直接计算每个 rank 的局部输出。K/V 收集模式目前支持非因果注意力，要求 `--ring-degree 1`。通过旧版 `UlyssesAttention` 适配器发起的 varlen 调用以及视频稀疏注意力不受支持。

当序列长度或视频形状让 DiT 前向过程成为瓶颈、且模型支持序列分片时，可以使用 SP。对延迟导向的多 GPU Qwen/Wan 部署，还要和 CFG 并行、FSDP 做对比；SP 并不自动是每个模型最好的多 GPU 方案。

<Note>
💡 AI Infra 学习笔记：扩散模型的序列并行与 LLM 的序列并行思路相通——注意力计算的开销随序列长度呈平方级增长，视频生成里一个 batch 的潜空间序列可能长达数万 token，单卡装不下或算不动。SP 把序列切成多份、分给多块 GPU，注意力阶段再通过 all-to-all（Ulysses）或 K/V all-gather（KV gather）交换数据。它的代价是通信开销随 SP 度数增长，所以"何时从单卡切到 SP、SP 度数取多少"是典型的容量-延迟权衡题。相比 LLM 的 KV 缓存，扩散 SP 分的是激活序列本身，这也是两者在面试考点上的区别。
</Note>

两种交换方式没有绝对优劣。K/V 收集省掉了反向 all-to-all，当它的局部注意力形状或集合通信更高效时可能有帮助；而 Ulysses 能减少注意力激活内存。请在目标模型、分辨率、加速器和互连上分别做基准测试。

对 SP 度数 `P`，K/V 收集相对 Ulysses 的单 rank 近似网络负载是 `P / 2`（不含各 rank 的局部分片）。因此 SP2 时两者负载相近，SP4 时 K/V 收集大约多传 2 倍数据，SP8 时多传 4 倍。当 all-gather 和它的局部注意力布局更高效时，K/V 收集仍可能更快，尤其是在低 SP 度数下；但这种扩展性让互连和输入形状也成为选型策略的一部分。

## 推荐命令

### Ulysses 序列并行

不使用环形并行时，默认模式只需要总 SP 度数：

```bash
sglang serve \
  --model-path Qwen/Qwen-Image \
  --num-gpus 4 \
  --sp-degree 4 \
  --port 8898
```

### K/V 收集序列并行

使用相同的 SP 进程组布局，显式选择另一种注意力交换方式：

```bash
sglang serve \
  --model-path Qwen/Qwen-Image \
  --num-gpus 4 \
  --sp-degree 4 \
  --sp-attention-mode kv_gather \
  --port 8898
```

### 张量加序列并行

TP 和 SP 使用相互独立的维度。禁用 DP 和 CFG 并行时，所需 GPU 数为 `tp_size * sp_degree`。下面的例子在两 rank 的 SP 维度上创建两个 TP 组：

```bash
sglang serve \
  --model-path Qwen/Qwen-Image \
  --num-gpus 4 \
  --tp-size 2 \
  --sp-degree 2 \
  --sp-attention-mode kv_gather \
  --port 8898
```

省略 `--sp-attention-mode kv_gather`，则在相同的 `tp=2, sp=2` 拓扑上使用 TP 加 Ulysses。

#### TP 加 SP 如何工作

TP 和 SP 构成 DiT 进程网格上两个正交的维度。对 `tp=2, sp=2`，rank `[0, 1]` 和 `[2, 3]` 是 TP 组，而 rank `[0, 2]` 和 `[1, 3]` 是 SP 组。因此每个 rank 同时属于两种组各一个：

- TP 分片受支持的注意力和 MLP 投影权重与计算，然后在 TP 组内部通信部分投影结果。
- SP 分片潜空间序列和注意力激活，然后在 SP 组内部使用 Ulysses 或 K/V 收集。

纯 SP 会在每个 SP rank 上复制 DiT 权重。加 TP 能降低每个 rank 上被 TP 分片的权重所占内存，同时保留 SP 的序列激活分片，代价是给每个适用的 DiT 块增加 TP 通信。具体能省多少内存取决于模型，因为并非每个参数或运行时缓冲区都会被 TP 分片。

因此 TP 加 SP 应该被当作一个容量与内存-延迟的帕累托选项，而不是默认的延迟最优解。在单 NVSwitch 节点上，当完整 DiT 权重能装进每块 GPU 时，纯 SP 常常胜出，因为它避免了重复的 TP 集合通信。当纯 SP 装不下、需要更多内存余量、或实测的内存节省值得那一点延迟增加时，再尝试 TP 加 SP。

下面这些有代表性的 eager 结果来自单 NVSwitch 节点上的八块 H200。时间取调度器侧端到端延迟的中位数。它们用于说明权衡关系，而不是定义通用策略：

| 模型与负载 | 实测最快拓扑 | TP 加 SP 帕累托点 | 权衡 |
| --- | --- | --- | --- |
| Qwen-Image, 1536x1536 | CFG2xSP4 Ulysses: 972.6 ms, 62.8 GiB/GPU | CFG2xTP2xSP2 K/V: 1017.4 ms, 48.4 GiB/GPU | 慢 4.6%，峰值内存降低 22.9% |
| Wan2.2-A14B, 832x480x81 | CFG2xSP4 K/V: 6573.5 ms, 61.9 GiB/GPU | CFG2xTP2xSP2 K/V: 7243.1 ms, 34.2 GiB/GPU | 慢 10.2%，峰值内存降低 44.7% |
| LTX2.3, 768x512x241 | SP8 K/V: 7258.2 ms, 55.4 GiB/GPU | TP2xSP4 K/V: 10372.3 ms, 37.8 GiB/GPU | 慢 42.9%，峰值内存降低 31.8% |

即使在某个拓扑不是全局延迟最优解时，K/V 收集仍可能改善同一拓扑下的 TP 加 SP。在同一实验中，相对 Ulysses，它对 TP2xSP4 的 FLUX 提升了 4.2%、LTX2.3 提升了 8.4%，对 CFG2xTP2xSP2 的 Qwen-Image 提升了 6.0%、Wan2.2-A14B 提升了 2.7%。请始终对比完整候选集（包括纯 SP、TP、CFG 及它们可行的组合），而不是先选定 SP 注意力后端。

### FSDP 加序列并行

FSDP 可以在参与 SP 的同一批 worker 上分片 DiT 权重。与 TP 乘 SP 不同，FSDP 和 SP 的度数不会相乘所需的 GPU 数。当纯 SP 足够快、但复制的 DiT 权重或长序列激活留下的内存余量太少时，这种方式很有用：

```bash
sglang serve \
  --model-path Lightricks/LTX-2.3 \
  --num-gpus 2 \
  --use-fsdp-inference true \
  --sp-degree 2 \
  --sp-attention-mode kv_gather \
  --port 8898
```

FSDP 会引入权重 all-gather 通信，所以当两者都装得下时，请与纯 SP 对比。在 FSDP 下，K/V 收集同样受非因果和 `ring_degree=1` 的约束。

### 环形序列并行

下面的例子用两块 GPU，`sp=2`、`ulysses=1`、`ring=2`。

```bash
sglang serve \
  --model-path Wan-AI/Wan2.2-TI2V-5B-Diffusers \
  --num-gpus 2 \
  --sp-degree 2 \
  --ulysses-degree 1 \
  --ring-degree 2 \
  --port 8898
```

### 单 GPU 基线

在把收益归因于序列并行之前，先用显式的单 GPU 基线：

```bash
sglang serve \
  --model-path Wan-AI/Wan2.2-TI2V-5B-Diffusers \
  --num-gpus 1 \
  --sp-degree 1 \
  --ulysses-degree 1 \
  --ring-degree 1 \
  --port 8898
```

## 基准测试建议

对 SP 做基准测试时，对比相同的模型、精度、分辨率、帧数、步数、调度器设置、提示词类型和输出路径。同时报告阶段延迟和 GPU 峰值内存；SP 在降低单 GPU 内存的同时会增加通信开销。

有用的指标：

- 端到端延迟
- 去噪阶段延迟
- 解码阶段延迟
- GPU 峰值内存与峰值已分配内存
- 可用的通信或运行时开销
