欢迎来到 **SGLang**！感谢你对贡献的兴趣。本指南简洁地介绍了如何搭建环境、运行测试、构建文档以及提交 Pull Request（PR）。无论你是在修一个小 bug 还是在开发一个重大特性，我们都建议遵循这些步骤，让贡献过程更顺畅。

## 从源码安装 SGLang

### Fork 并克隆仓库

**注意**：新贡献者**没有**向官方 SGLang 仓库推送的写权限。请在你的 GitHub 账号下 fork 该仓库，然后在本地克隆你的 fork。

```bash
git clone https://github.com/<your_user_name>/sglang.git
```

### 从源码构建

请参考 [从源码安装 SGLang](../get-started/install#method-2-from-source)。

## 用 pre-commit 格式化代码

我们使用 [pre-commit](https://pre-commit.com/) 来维持一致的代码风格检查。在推送改动之前，请运行：

```bash
pip3 install pre-commit
pre-commit install
pre-commit run --all-files
```

- **`pre-commit run --all-files`** 会手动运行所有配置好的检查，并在可能时自动修复。如果第一次运行失败，请重跑一次，确保 lint 错误被完全解决。请确保你的代码在**创建 Pull Request 之前**通过所有检查。
- **不要**直接提交到 `main` 分支。始终新建一个分支（例如 `feature/my-new-feature`），推送你的改动，然后从该分支发起 PR。
- lychee 的链接检查在 CI 中**强制执行**。默认情况下它不阻塞本地提交。
- 要手动运行本地链接检查，请用：`pre-commit run --hook-stage manual lychee --all-files`。

## 运行和添加单元测试

如果你添加了新功能或修复了 bug，请添加相应的单元测试，以确保覆盖并防止回归。

### 单元测试（无需服务端）

单元测试位于 [`test/registered/unit/`](https://github.com/sgl-project/sglang/tree/main/test/registered/unit)，目录结构与 `python/sglang/srt/` 源码树一一对应。这些测试**无需**启动服务端或加载真实模型权重即可验证组件逻辑。
SGLang 使用 Python 内置的 [unittest](https://docs.python.org/3/library/unittest.html) 框架，并用 [pytest](https://docs.pytest.org/) 作为测试运行器。

**什么时候添加单元测试：** 如果你修改了 `python/sglang/srt/` 下的文件，请检查 `test/registered/unit/` 中是否有对应的测试，并为你的改动补充覆盖。例如：

```
srt/mem_cache/radix_cache.py   →  unit/mem_cache/test_radix_cache.py
srt/sampling/sampling_params.py →  unit/sampling/test_sampling_params.py
```

**在本地运行单元测试：**

```bash Command
pytest test/registered/unit/ -v                # all unit tests
pytest test/registered/unit/mem_cache/ -v      # one module
```

**带覆盖率运行：**

```bash Command
pytest test/registered/unit/ --cov --cov-config=.coveragerc -v
```

关于 CI 注册的约定、测试结构与示例，参见 [`test/registered/unit/README.md`](https://github.com/sgl-project/sglang/tree/main/test/registered/unit/README.md)。

### E2E 测试（需要服务端）

对于需要启动服务端的测试，请参考 [`test/registered/README.md`](https://github.com/sgl-project/sglang/tree/main/test/registered/README.md) 了解测试应放在哪里。

关于运行测试及接入 CI 的详细说明，请参考 [test/README.md](https://github.com/sgl-project/sglang/tree/main/test/README.md)。

## 测试精度
如果你的代码改动会改变模型输出，请运行精度测试。一个快速的冒烟检查是 few-shot GSM8K。

```text Output
# Launch a server
python3 -m sglang.launch_server --model Qwen/Qwen2-7B-Instruct

# Evaluate
python3 -m sglang.test.few_shot_gsm8k --num-questions 200
```

请注意，上面的脚本主要是一个冒烟检查，并不是严格的精度或速度测试。
由于批处理以及推理引擎的非确定性，该测试的精度可能有明显波动（1%–5%）。
另外，不要依赖该脚本输出的 "Latency/Output throughput"，它不是严谨的速度测试。

对当前最先进的模型来说，GSM8K 已经太简单了。请自行尝试更有挑战性的精度测试。
更多的精度评估示例见：
- [test_eval_accuracy_large.py](https://github.com/sgl-project/sglang/blob/main/test/manual/eval/test_eval_accuracy_large.py)
- [test_gpt_oss_1gpu.py](https://github.com/sgl-project/sglang/blob/main/test/manual/core/test_gpt_oss_1gpu.py)

## 如何触发 CI 测试

我们有很多开放的 PR，但 CI 机器有限，所以只有高层级和受信任的贡献者才有权限触发 CI 测试。
有权限的用户列在 [CI_PERMISSIONS.json](https://github.com/sgl-project/sglang/blob/main/.github/CI_PERMISSIONS.json)。

**PR 作者**总是可以在自己的 PR 上使用 `/rerun-failed-ci`，即使他们不在 `CI_PERMISSIONS.json` 里。

要让 CI 在某个 pull request 上运行，它必须带有 "run-ci" 标签。授权用户可以添加该标签，或通过在 PR 上评论以下命令来重跑失败的测试：

- `/tag-run-ci-label`：添加 "run-ci" 标签。只有**后续**的提交会触发 CI；当前提交不受影响。加上 `extra` 参数（`/tag-run-ci-label extra`）可以额外应用 "run-ci-extra" 标签，让 PR 加入额外测试工作流（`pr-test-extra.yml`）。
- `/rerun-failed-ci`：以 **failed、flaky 或 skipped** 为结论，重跑最新提交对应的工作流。
- `/tag-and-rerun-ci`：同时执行上面两个动作。在新的 PR 上用它来让当前提交触发 CI——单独用 `/tag-run-ci-label` 不会触发当前提交。同样接受 `extra` 参数（`/tag-and-rerun-ci extra`）。
- `/rerun-stage <stage-name>`：重跑单个测试阶段，无需等待其依赖。适合快速验证某个具体的测试修复，而不用等待前面阶段约 30 分钟。
- `/rerun-test <test-spec> [<test-spec> ...]`：直接重跑一个或多个具体测试，绕过阶段边界。每个 `<test-spec>` 是 pytest 风格的 `<file>::<TestClass>[.<test_method>]`（`::TestClass` 与 `.<test_method>` 部分可选）。处理器会解析每个 spec，按注册的 runner-label 分组，并为每组分发一个 [Rerun Test workflow](https://github.com/sgl-project/sglang/actions/workflows/rerun-test.yml)。示例：`/rerun-test test_srt_endpoint.py`、`/rerun-test registered/core/test_srt_endpoint.py::TestSRTEndpoint.test_simple_decode`、`/rerun-test test_a.py test_b.py`（一次多个）。

如果你有权限，[Slash Command Handler](https://github.com/sgl-project/sglang/actions/workflows/slash-command-handler.yml) 会执行你的命令，并在你的评论上点赞 👍。反应出现可能需要几分钟。用法见这个[示例](https://github.com/sgl-project/sglang/pull/14253#issuecomment-3599509302)。

为了避免在 PR 上堆太多 `/rerun-failed-ci` 评论，你也可以通过编辑已有评论并追加任意后缀来触发该命令（例如 `/rerun-failed-ci try again`）。

重跑单个测试阶段的示例：`/rerun-stage unit-test-backend-4-gpu`。

如果你没有权限也不是 PR 作者，请让维护者帮你触发 CI。

### CI 速率限制

由于 CI 调度和资源有限，高优先级 PR 可能会抢占正在运行的任务。这种情况下，你可能需要重跑测试。
我们设置 CI 速率限制是为了防止滥用，并确保 CI 资源的公平使用。

每个 CI 工作流在其工作流配置文件中定义了默认限制。例如在 [pr-gate.yml](https://github.com/sgl-project/sglang/blob/main/.github/workflows/pr-gate.yml) 中，默认冷却期为 120 分钟，每个工作流可以通过 `cool-down-minutes` 输入参数覆盖它：

```yaml Config
cool-down-minutes:
  description: "Default cooldown period in minutes; 0 disables rate limiting"
  type: number
  default: 120
```

列在 [CI_PERMISSIONS.json](https://github.com/sgl-project/sglang/blob/main/.github/CI_PERMISSIONS.json) 中的用户可能有各自的冷却间隔。实践中，我们取工作流默认窗口与用户特定间隔的最小值。

## 代码风格指南
- 避免代码重复。如果同一段代码（超过五行）多次出现，把它提取成共享函数。
- 尽量减少设备同步。尽可能减少昂贵的 CPU-GPU 同步操作，例如 `tensor.item()` 或 `tensor.cpu()`。尽量使用向量化代码。
- 优先考虑极致效率。SGLang 是一个运行时，你写的大部分代码都在每个请求的关键路径上。尽可能优化所有小的开销，尤其是模型前向代码。
  - 一个常见模式是模型前向过程中的一些运行时检查（例如[这里](https://github.com/sgl-project/sglang/blob/f1b0eda55c2c4838e8ab90a0fac7fb1e3d7064ab/python/sglang/srt/models/deepseek_v2.py#L486-L491)）。这些检查在每一层几乎都一样。请尽可能在 `__init__` 里把结果缓存成一个布尔值。

<Note>
💡 AI Infra 学习笔记：这条「减少设备同步」是推理引擎性能优化的核心原则之一。GPU 是异步执行模型，`tensor.item()`/`tensor.cpu()` 会强制 CPU 等待 GPU 完成（同步点），打断流水线、浪费宝贵的并行度。面试中常考的问题「为什么 GPU 利用率上不去」的一大根因就是频繁同步。任何在模型前向里按 token/层循环的 Python 级检查，都会成为吞吐瓶颈。
</Note>

- 尽量让函数保持纯净。避免就地修改参数。
- 保持文件简洁。如果某个文件超过 2000 行代码，把它拆成多个小文件（例如 `scheduler.py`、`scheduler_output_processor_mixin.py`）。
- 在文件里，把核心数据结构放在文件顶部，工具函数放在底部。
- 让测试保持快速。
  - 如果单个测试文件运行超过 500 秒，把它拆成多个小文件（例如 `test_eagle_infer_a.py`、`test_eagle_infer_b.py`）。
  - 如果 github workflow 里的单个 job 运行超过 30 分钟，把它拆成更小的 job/step。
  - 在单元测试中复用服务端启动，让测试跑得更快。
- 绝不要用 `pickle.loads()`、`pickle.load()` 或 `recv_pyobj()` 反序列化不可信或网络接收的数据。Python 的 [pickle 模块不安全](https://docs.python.org/3/library/pickle.html)——它在反序列化时可能执行任意代码。请使用 [msgpack](https://github.com/jcrist/msgspec) 或 JSON 等安全序列化格式。
- 支持新硬件或新特性时，遵循以下准则：
  - 不要大幅改动现有代码。
  - 始终优先用新文件来引入针对你新硬件的特定组件（例如 `allocator_ascend.py`）。
  - 如果你为某个新特性写多个 if/else 分支，确保公共路径（例如 NVIDIA 硬件或现有代码路径）是第一个分支。

## 如何更新 sgl-kernel
由于 sglang 与 `sglang-kernel`（原 `sgl-kernel`）发行版是两个独立的 Python 包，我们当前的 GitHub CI 基础设施不支持在同一个 pull request（PR）里更新 kernel 并立即使用它。
要在 `python/sglang/kernels/aot/` 源码树中添加新 kernel 或修改现有 kernel，你必须使用多个 PR。

按以下步骤操作：

1. 提交一个更新 sgl-kernel 源码的 PR，但暂时不要在 sglang Python 包中使用它（例如 [#8884](https://github.com/sgl-project/sglang/pull/8884/files)）。
2. 提升 kernel 包的版本号（例如 [#9220](https://github.com/sgl-project/sglang/pull/9220/files)）。
   - 合并后会自动触发 `sglang-kernel` wheel 包发布到 PyPI。
   - 如果不急，可以等其他人发布 wheel 包。新版本通常一周内会发布。
3. 应用改动：
   - 更新 `sglang/python/pyproject.toml` 里的 `sglang-kernel` 版本，以使用修改后的 kernel。
   - 更新 sglang 中相关的调用代码，以使用新 kernel。

<Note>
💡 AI Infra 学习笔记：sgl-kernel 与 sglang 分开发版，本质上是「AOT 预编译 kernel 与 Python 业务代码解耦」的工程决策——kernel 二进制需要针对不同 CUDA 版本预编译，改动后要等 wheel 发布才能被主包消费。这也是 AI Infra 里常见的发布节奏：底层算子库（如 FlashInfer、cuDNN、TensorRT-LLM）都独立于上层框架发版。
</Note>
