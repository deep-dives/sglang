本指南介绍如何在 SGLang 中添加或重构量化支持。它重点关注仅权重量化和权重-激活量化方法的通用结构，例如 AWQ、GPTQ、compressed-tensors、ModelSlim、Quark 以及相关的后端 kernel。

## 设计目标

量化代码应该把量化格式的语义与硬件相关的执行分开。这样可以更容易地添加新格式、跨格式复用 kernel，并独立审查平台相关的改动。

请遵循 [Quantization Modifications](https://github.com/sgl-project/sglang/issues/15194) 中提出的架构：

- **Config（配置）**：解析模型与运行时的量化参数，校验支持的选项，并选择合适的方案。
- **Scheme（方案）**：负责量化权重的创建、权重加载、后处理，以及 Linear、MoE、embedding 或其他模块类型的量化层接线。
- **Backend kernel（后端 kernel）**：封装硬件相关的执行、布局转换、kernel 选择与 kernel 调用，面向 GPU（CUDA/HIP/XPU）、NPU 或其他后端。

<Note>
💡 AI Infra 学习笔记：把「量化格式语义」与「硬件执行」分离，是推理引擎里典型的抽象分层思路。量化方案（如何存权重、按什么 scale 反量化）相对稳定，而 kernel 要跟着 GPU 代际和算子库演进——两者解耦后，新增一种格式只需写新的 scheme，新增一种硬件只需写新的 kernel，改动面互相隔离。
</Note>

避免把配置解析、权重加载和后端 kernel 调用都塞进一个巨型文件。如果一个方法需要多种格式或多个后端，就在 `python/sglang/srt/layers/quantization/<method>/` 下新增一个包，并把各方案拆分到 `schemes/`。

## 推荐的文件布局

对包含多个方案或后端专用执行路径的量化方法，使用如下布局：

```text
python/sglang/srt/layers/quantization/<method>/
  __init__.py
  <method>.py
  schemes/
    __init__.py
    <method>_scheme.py
    <method>_linear.py
    <method>_moe.py
    <method>_<variant>.py
```

后端 kernel 应该放在它们所针对的硬件后端下：

```text
python/sglang/srt/hardware_backend/gpu/quantization/<method>_kernels.py
python/sglang/srt/hardware_backend/npu/quantization/<method>_kernels.py
```

把共享的方法选择逻辑留在量化包内，并保持后端导入范围尽量窄。这样可以避免循环导入，也能防止非目标平台导入不可用的 kernel 依赖。

## 添加或重构量化方法

1. 定义配置入口，并在需要时通过 `python/sglang/srt/layers/quantization/__init__.py` 注册。
2. 添加明确的方案选择辅助函数，例如 `get_linear_scheme` 和 `get_moe_scheme`。
3. 把层相关的权重创建与权重加载移入 scheme 类。
4. 把 GPU（CUDA/HIP/XPU）、NPU 或其他硬件的 kernel 调用移入后端 kernel 模块。
5. 显式区分 Linear、MoE、embedding 以及非线性模块的处理。不要把某个 Linear 量化方法套用到语义不同的模块类型上。
6. 保持对现有量化检查点和运行时参数的兼容。
7. 添加同时覆盖配置解析与改动涉及的执行路径的测试。

示例可参考 AWQ 和 GPTQ 的重构：

- [PR #21126](https://github.com/sgl-project/sglang/pull/21126)：把 AWQ 的 scheme、权重初始化与后端 kernel 调用拆分。
- [PR #26402](https://github.com/sgl-project/sglang/pull/26402)：把同样的 scheme/kernel 拆分应用到 GPTQ。

## 测试与验证

量化改动既可能影响精度，也可能影响性能。请提供与改动影响范围相匹配的验证。

对仅涉及 Python 结构的改动：

```bash
ruff check <changed-python-files>
git diff --check
```

对量化模型行为的验证：

- 为每个被改动的量化方法至少启动一个有代表性的模型。
- 发送一个 `/generate` 请求，确认输出路径正常走通。
- 如果改动可能影响数值结果，运行一次精度冒烟测试。
- 如果改动涉及 kernel 调用、布局转换或分发逻辑，附上带预热的基准测试结果。

对后端相关改动：

- 在受支持的 GPU 环境（NVIDIA、AMD 或 Intel）上验证 GPU 改动。
- 在受支持的 Ascend 环境上验证 NPU 改动。
- 在 PR 描述中写明用到的确切模型、量化参数、后端参数、硬件和命令。

## PR 检查清单

在请求评审之前，确保 PR 描述包含以下内容：

- 被改动的量化方法与后端路径。
- 该 PR 所依据的 issue、设计提案或路线图条目。
- 对现有检查点或参数的任何兼容性说明。
- 当模型输出可能变化时的精度结果。
- 当运行时性能可能变化时的基准测试或性能剖析结果。
- 实际运行过的本地检查与模型启动测试。

源码搭建、格式化、单元测试、CI 触发与评审流程的细节，请使用通用的 [贡献指南](./contribution_guide)。
