本指南介绍如何用 `python -m sglang.bench_serving` 基准测试在线服务化的吞吐量与延迟。它通过 OpenAI 兼容端点和原生端点支持多种推理后端，并同时输出控制台指标和可选的 JSONL 结果。

### 它的作用

- 生成合成提示词或基于数据集的提示词，提交给目标服务化端点
- 测量吞吐量、首 token 时间（TTFT）、token 间延迟（ITL）、每个请求的端到端延迟等
- 支持流式或非流式模式、速率控制与并发限制

### 支持的后端与端点

- `sglang` / `sglang-native`：`POST /generate`
- `sglang-oai`、`vllm`、`lmdeploy`：`POST /v1/completions`
- `sglang-oai-chat`、`vllm-chat`、`lmdeploy-chat`：`POST /v1/chat/completions`
- `sglang-embedding`、`vllm-embedding`：`POST /v1/embeddings`
- `trt`（TensorRT-LLM）：`POST /v2/models/ensemble/generate_stream`
- `gserver`：自定义服务端（本脚本尚未实现）
- `truss`：`POST /v1/models/model:predict`

如果提供了 `--base-url`，请求就发给它。否则使用 `--host` 和 `--port`。当未提供 `--model` 时，脚本会尝试查询 `GET /v1/models` 以获取可用的模型 ID（OpenAI 兼容端点）。

### 前置条件

- Python 3.10+
- 本脚本常用的依赖：`aiohttp`、`numpy`、`requests`、`tqdm`、`transformers`，某些数据集还需要 `datasets`、`pillow`、`pybase64`。按需安装。
- 一个已启动且可通过上述端点访问的推理服务端
- 如果你的服务端需要认证，请设置环境变量 `OPENAI_API_KEY`（用作 `Authorization: Bearer <key>`）

### 快速开始

对暴露 `/generate` 端点的 sglang 服务端运行一个基础基准测试：

```bash Command
python3 -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct
```

```bash Command
python3 -m sglang.bench_serving \
  --backend sglang \
  --host 127.0.0.1 --port 30000 \
  --num-prompts 1000 \
  --model meta-llama/Llama-3.1-8B-Instruct
```

或者，使用 OpenAI 兼容端点（completions）：

```bash Command
python3 -m sglang.bench_serving \
  --backend vllm \
  --base-url http://127.0.0.1:8000 \
  --num-prompts 1000 \
  --model meta-llama/Llama-3.1-8B-Instruct
```

### 公平的 embedding 对比

用相同的模型、分词器、输入长度、提示词数量与并发度，分别使用两个 embedding 后端。基准测试报告输入 token 吞吐量与端到端延迟；embedding 没有解码侧的 TTFT 或 TPOT。

```bash Command
# Start either server on the same hardware and precision, then run one at a time.
python3 -m sglang.bench_serving \
  --backend sglang-embedding \
  --model google/embeddinggemma-300m \
  --dataset-name random \
  --random-input-len 2048 \
  --num-prompts 300 \
  --max-concurrency 64 \
  --warmup-requests 3 \
  --flush-cache
```

```bash Command
# vLLM's cache reset endpoint requires VLLM_SERVER_DEV_MODE=1 at server startup.
python3 -m sglang.bench_serving \
  --backend vllm-embedding \
  --model google/embeddinggemma-300m \
  --dataset-name random \
  --random-input-len 2048 \
  --num-prompts 300 \
  --max-concurrency 64 \
  --warmup-requests 3 \
  --flush-cache
```

`--flush-cache` 会在预热之后对 SGLang 调用 `/flush_cache`、对 vLLM 调用 `/reset_prefix_cache`。对 vLLM，请以 `VLLM_SERVER_DEV_MODE=1` 启动服务端；否则基准测试会大声失败，而不是意外测出热缓存的性能。

### 数据集

用 `--dataset-name` 选择：

- `sharegpt`（默认）：加载 ShareGPT 风格的对组；可选地用 `--sharegpt-context-len` 限制长度，并用 `--sharegpt-output-len` 覆盖输出长度
- `random`：随机文本长度；从 ShareGPT token 空间采样
- `random-ids`：随机 token id（可能产生乱码）
- `image`：生成图片并包装进聊天消息；支持自定义分辨率、多种格式与不同类型的内容
- `generated-shared-prefix`：带长共享系统提示词与短问题的合成数据集
- `mmmu`：从 MMMU（Math 子集）采样并包含图片
- `speed-bench`：[SPEED-Bench](https://huggingface.co/datasets/nvidia/SPEED-Bench)（**SPEculative Evaluation Dataset**）——用于评估[投机解码（SD）](https://arxiv.org/abs/2604.09557)算法的统一基准测试。使用 Throughput 子集，它提供固定长度的输入序列（1K–32K token），并按输出熵分为三个类别（`low_entropy`、`mixed`、`high_entropy`）。需要预先下载的 JSONL 文件，通过 `--dataset-path` 传入。
- `agentic-trace`：回放预构建的多轮 agentic trace（例如 OpenHands / SWE-smith）。每个对话逐轮回放，把服务端的真实助手回复喂回下一轮的历史中。需要聊天后端（`--backend sglang-oai-chat`）以及通过 `--dataset-path` 传入的 trace JSON。

常见数据集参数：

- `--num-prompts N`：请求数量
- `--random-input-len`、`--random-output-len`、`--random-range-ratio`：用于 random/random-ids/image
- `--image-count`：每个请求的图片数量（用于 `image` 数据集）。

- `--apply-chat-template`：构造提示词时套用分词器的对话模板
- `--dataset-path PATH`：ShareGPT JSON 的文件路径；如果留空且文件不存在，会下载并缓存

生成式共享前缀参数（用于 `generated-shared-prefix`）：

- `--gsp-num-groups`
- `--gsp-prompts-per-group`
- `--gsp-system-prompt-len`
- `--gsp-question-len`
- `--gsp-output-len`
- `--gsp-group-distribution {uniform,zipf}`：每个请求的前缀组采样分布（默认：`uniform`）。使用 `zipf` 时，每个请求的组按排名采样，`p(rank) = (1/rank**alpha) / sum_k(1/k**alpha)`；排名从 1 开始，组索引 0 最热。磁盘上的数据集缓存使用每个 `(group_distribution, zipf_alpha)` 单独一个键，所以 uniform 模式的缓存永远不会与 zipf 模式的缓存混用。
- `--gsp-zipf-alpha FLOAT`：`--gsp-group-distribution=zipf` 的 Zipf 指数。必须是严格大于 0 的有限浮点数；值越大，请求越集中在低排名（更热）的组上。当分布为 `zipf` 时必填；否则必须省略。

图片数据集参数（用于 `image`）：

- `--image-count`：每个请求的图片数量
- `--image-resolution`：图片分辨率；支持预设（4k、1080p、720p、360p）或自定义的 'heightxwidth' 格式（例如 1080x1920、512x768）
- `--image-format`：图片格式（jpeg 或 png）
- `--image-content`：图片内容类型（random 或 blank）

Agentic trace 参数（用于 `agentic-trace`）：

- `--dataset-path`：预构建 trace JSON 的路径
- `--sharegpt-output-len`：每轮输出长度（默认：220）
- `--dataset-offset`：采样前把对话列表旋转这么多条，这样连续的扫描轮次会从新的对话开始
- `--agentic-max-turns`：把每个对话限制为最多这么多轮（适合小规模、快速的性能剖析运行）

SPEED-Bench 参数（用于 `speed-bench`）：

- `--dataset-path PATH`：预下载的 SPEED-Bench Throughput JSONL 路径（例如 `throughput_1k.jsonl`）。用 [SPEED-Bench 测量框架](https://github.com/NVIDIA/Model-Optimizer/tree/main/examples/specdec_bench) 生成它。
- `--speed-bench-category`：过滤到单个熵类别：`low_entropy`、`mixed` 或 `high_entropy`（默认：全部）
- `--speed-bench-output-len`：每个请求的固定输出 token 数（默认：512）

### 选择模型与分词器

- 除非后端暴露了 `GET /v1/models`（此时会自动选择第一个模型 ID），否则 `--model` 是必填的。
- `--tokenizer` 默认等于 `--model`。两者都可以是 HF 模型 ID 或本地路径。
- 对于 ModelScope 工作流，设置 `SGLANG_USE_MODELSCOPE=true` 可以通过 ModelScope 获取模型（为提速会跳过权重）。
- 如果你的分词器没有对话模板，脚本会告警，因为对乱码输出做 token 计数可能不够可靠。

### 速率、并发与流式

- `--request-rate`：每秒请求数。`inf` 表示立即全部发送（突发）。非无限速率使用泊松过程决定到达时间。
- `--max-concurrency`：无论到达速率如何，都限制在途请求的上限。
- `--disable-stream`：在支持的情况下切换到非流式模式；此时对 chat completions，TTFT 就等于总延迟。

### 其他关键选项

- `--output-file FILE.jsonl`：把 JSONL 结果追加到文件；未指定时自动命名
- `--output-details`：包含每个请求的数组（生成的文本、错误、ttfts、itls、输入/输出长度）
- `--extra-request-body '&#123;"top_p":0.9,"temperature":0.6&#125;'`：合并进请求体（采样参数等）
- `--disable-ignore-eos`：透传 EOS 行为（各后端不同）
- `--warmup-requests N`：先运行带短输出的预热请求（默认 1）
- `--flush-cache`：主运行前调用 `/flush_cache`（sglang）
- `--profile`：调用 `/start_profile` 和 `/stop_profile`（要求服务端启用性能剖析，例如 `SGLANG_TORCH_PROFILER_DIR`）
- `--lora-name name1 name2 ...`：每个请求随机选一个并传给后端（例如 sglang 的 `lora_path`）
- `--tokenize-prompt`：发送整数 ID 而不是文本（目前仅支持 `--backend sglang`）

### 指标说明

每次运行后会打印：

- 请求吞吐量（req/s）
- 输入 token 吞吐量（tok/s）——同时包含文本与视觉 token
- 输出 token 吞吐量（tok/s）
- 总 token 吞吐量（tok/s）——同时包含文本与视觉 token
- 输入文本 token 总数与输入视觉 token 总数——按模态细分
- 并发度：所有请求的累计时间除以墙钟时间
- 端到端延迟（ms）：每个请求总延迟的 mean/median/std/p99
- 首 token 时间（TTFT，ms）：流式模式下的 mean/median/std/p99
- token 间延迟（ITL，ms）：token 之间的 mean/median/std/p95/p99/max
- TPOT（ms）：首个 token 之后的 token 处理时间，即 `(latency - ttft)/(tokens-1)`
- 接受长度（仅 sglang，如有）：投机解码的接受长度

脚本还会用配置的分词器对生成的文本重新分词，并报告 "retokenized" 计数。

<Note>
💡 AI Infra 学习笔记：这几个指标对应 LLM 推理性能的三个观察维度——TTFT（首 token 时间）反映「预填充阶段 + 调度排队」快不快，决定用户等多久看到第一个字；ITL 反映解码阶段连续 token 之间的间隔（流式体感的顺滑度）；TPOT 是单 token 处理时间，是解码吞吐的倒数形式。做性能优化时要分清瓶颈在哪一端：预填充重计算、解码重显存带宽，对应的优化手段完全不同。
</Note>

### JSONL 输出格式

设置 `--output-file` 后，每次运行追加一个 JSON 对象。基础字段：

- 参数摘要：backend、dataset、request_rate、max_concurrency 等
- 时长与总数：completed、total_input_tokens、total_output_tokens、retokenized 总数
- 与控制台输出一致的吞吐量与延迟统计
- 可用时（sglang）`accept_length`

使用 `--output-details` 时，扩展对象还包含数组：

- `input_lens`、`output_lens`
- `ttfts`、`itls`（每个请求：ITL 数组）
- `generated_texts`、`errors`

Zipf / 幂律前缀热度（通过 `--gsp-group-distribution=zipf` 启用）：

```bash Command
python3 -m sglang.bench_serving \
  --backend sglang \
  --host 127.0.0.1 --port 30000 \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name generated-shared-prefix \
  --gsp-num-groups 64 --gsp-prompts-per-group 16 \
  --gsp-system-prompt-len 2048 --gsp-question-len 128 --gsp-output-len 256 \
  --gsp-group-distribution zipf --gsp-zipf-alpha 1.2 \
  --seed 42
```

`zipf` 模式从基于排名的分布 `p(rank) = (1/rank**alpha) / sum_k(1/k**alpha)` 中采样每个请求的前缀组，排名从 1 开始，所以组索引 0 最热。请求总数保持为 `num_groups * prompts_per_group`——与 `uniform` 模式完全一致——只有每个请求的组分配变了。`alpha` 必须是严格大于 0 的有限浮点数；值越大，请求越集中在低排名（更热）的组上。

位于 `~/.cache/sglang/benchmark/gen_shared_prefix_*.pkl` 的磁盘数据集缓存在键中包含 `group_distribution` 和 `zipf_alpha`，所以 uniform 模式与 zipf 模式的运行（或两个不同 alpha 的 zipf 运行）永远不会共享缓存文件。uniform 模式的文件名与旧格式一致，因此已有缓存仍然有效。

该参数只控制前缀热度的分布形状。它本身并不复现任何生产 trace，也不保证某个引擎能达到某个缓存命中率。
