SGLang 基于 OpenTelemetry Collector 导出请求追踪数据。启动服务器时加上 `--enable-trace` 即可启用追踪，并用 `--otlp-traces-endpoint` 配置 OpenTelemetry Collector 的端点。

可视化效果的示例截图见 https://github.com/sgl-project/sglang/issues/8965。

<Note>
💡 AI Infra 学习笔记：请求级链路追踪（request tracing）把一次推理请求拆成一个个可观测的时间片（slice）——分词、调度、预填充、解码、采样、网络传输等，逐段记录耗时。推理引擎是高度并发的系统，一次请求会在多个线程、多个进程之间流转，光看整体延迟很难定位瓶颈；有了链路追踪，就能精确回答“时间到底花在了哪一步”。它是排查长尾延迟、跨节点（如 PD 分离）问题的核心基础设施。
</Note>

## 配置指南

本节介绍如何配置请求追踪并导出追踪数据。

1. 安装所需的包和工具
    * 安装 Docker 和 Docker Compose
    * 安装依赖
    ```bash Command
    # enter the SGLang root directory
    pip install -e "python[tracing]"

    # or manually install the dependencies using pip
    pip install opentelemetry-sdk opentelemetry-api opentelemetry-exporter-otlp opentelemetry-exporter-otlp-proto-grpc
    ```

2. 启动 OpenTelemetry Collector 和 Jaeger
    ```bash Command
    docker compose -f examples/monitoring/tracing_compose.yaml up -d
    ```

3. 以开启追踪的方式启动 SGLang 服务器
    ```bash Command
    # set env variables
    export SGLANG_OTLP_EXPORTER_SCHEDULE_DELAY_MILLIS=500
    export SGLANG_OTLP_EXPORTER_MAX_EXPORT_BATCH_SIZE=64
    # start the prefill and decode server
    python -m sglang.launch_server --enable-trace --otlp-traces-endpoint 0.0.0.0:4317 <other option>
    # start the model-gate-way
    python -m sglang_router.launch_router --enable-trace --otlp-traces-endpoint 0.0.0.0:4317 <other option>
    ```

    把 `0.0.0.0:4317` 换成 OpenTelemetry Collector 的实际端点。如果你用 tracing_compose.yaml 启动了 OpenTelemetry Collector，默认接收端口就是 4317。

    要使用 HTTP/protobuf 方式的 span 导出器，请设置以下环境变量，并指向一个 HTTP 端点，例如 `http://0.0.0.0:4318/v1/traces`。
    ```bash Command
    export OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
    ```

4. 发送一些请求

5. 观察追踪数据是否成功导出
    * 用浏览器访问 Jaeger 的 16686 端口，可视化查看请求追踪。
    * OpenTelemetry Collector 还会把追踪数据以 JSON 格式导出到 /tmp/otel_trace.json。在后续的补丁中，我们会提供一个工具，把这些数据转换为 Perfetto 兼容格式，以便在 Perfetto UI 中可视化请求。

6. 动态调整追踪级别
    追踪级别可配置为 `0` 到 `3`，各取值的含义如下：
    ```
    0: disable tracing
    1: Trace important slices
    2: Trace all slices except nested ones
    3: Trace all slices (default)
    ```
    **启动时** —— 在启动服务器前设置 `SGLANG_TRACE_LEVEL`：
    ```bash Command
    SGLANG_TRACE_LEVEL=2 python -m sglang.launch_server --enable-trace --otlp-traces-endpoint 0.0.0.0:4317 <other options>
    ```

    **运行时** —— 无需重启，通过 HTTP API 动态调整：
    ```bash Command
    curl http://0.0.0.0:30000/set_trace_level?level=2
    ```
    把 `0.0.0.0:30000` 换成你实际的服务器地址，并把 `level=2` 换成你想要设置的级别。

    **注意**：必须先设置 `--enable-trace` 参数，否则无论怎么动态调整追踪级别，追踪能力都不会生效。

<Note>
💡 AI Infra 学习笔记：追踪分级（trace level）本质是“采样粒度与开销”的权衡——级别越高，记录的 slice 越多，定位越细，但采集、序列化、网络传输的开销也越大。因此 SGLang 支持运行时动态降级：先全量抓问题，再调回低级别长期运行。这也是可观测性系统设计的通用思路：观测本身也是成本，要按需开合。
</Note>

## 如何为你关心的 slice 添加追踪？（API 介绍）

我们已经在分词器和调度器的主线程中插入了埋点。如果你想追踪更多的请求执行片段，或做更细粒度的追踪，请使用下面介绍的 tracing 包提供的 API。

**下面所有实现都在 python/sglang/srt/observability/req_time_stats.py 中完成。想新增 slice，就在这里加。**

1. 初始化

    初始化阶段，每个参与追踪的进程都应执行：
    ```python Example
    process_tracing_init(otlp_traces_endpoint, server_name)
    ```
    otlp_traces_endpoint 从启动参数中获取，server_name 可以随意设置，但要在所有进程间保持一致。

    初始化阶段，每个参与追踪的线程都应执行：
    ```python Example
    trace_set_thread_info("thread label", tp_rank, dp_rank)
    ```
    “thread label” 可以看作线程的名字，用来在可视化视图中区分不同线程。

2. 为请求创建追踪上下文

    每个请求都需要调用 `TraceReqContext()` 初始化请求上下文，用来生成 slice 的 span 并记录请求阶段信息。你可以把它存在请求对象里，也可以维护成全局变量。

3. 标记请求的开始与结束
    ```
    trace_ctx.trace_req_start().
    trace_ctx.trace_req_finish()
    ```
    trace_req_start() 和 trace_req_finish() 必须在同一个进程内调用，例如在分词器中。

4. 为 slice 添加追踪

    * 常规地为 slice 添加追踪：
        ```python Example
        trace_ctx.trace_slice_start(RequestStage.TOKENIZER.stage_name)
        trace_ctx.trace_slice_end(RequestStage.TOKENIZER.stage_name)

        or
        trace_ctx.trace_slice(slice: TraceSliceContext)
        ```

    - 线程中最后一个 slice 结束时，必须用 thread_finish_flag=True 标记，或显式调用 trace_ctx.abort()；否则该线程的 span 无法正确生成。
        ```python Example
        trace_ctx.slice_end(RequestStage.D.stage_name, thread_finish_flag = True)
        trace_ctx.abort()
        ```

5. 当请求执行流转到另一个线程时，需要显式重建线程上下文
    - receiver（接收方）：通过 ZMQ 收到请求后，执行以下代码：
        ```python Example
        trace_ctx.rebuild_thread_context()
        ```

## 如何扩展追踪框架以支持更复杂的追踪场景

当前提供的 tracing 包还有进一步发展的空间。如果你想在此基础上构建更高级的功能，需要先理解它现有的设计原则。

追踪框架实现的核心在于 span 结构和追踪上下文的设计。为了把分散的 slice 聚合起来，并支持并发追踪多个请求，我们设计了三级追踪上下文（或者说 span）结构：`TraceReqContext`、`TraceThreadContext` 和 `TraceSliceContext`。它们的关系如下：
```
TraceReqContext (req_id="req-123")
├── TraceThreadContext(thread_label="scheduler", tp_rank=0)
|     └── TraceSliceContext(slice_name="prefill")
|
└── TraceThreadContext(thread_label="scheduler", tp_rank=1)
      └── TraceSliceContext(slice_name="prefill")
```

每个被追踪的请求维护一个全局的 `TraceReqContext`，并创建对应的请求 span。处理该请求的每个线程都会记录一个 `TraceThreadContext` 并创建线程 span。`TraceThreadContext` 嵌套在 `TraceReqContext` 之下；每个当前被追踪的代码 slice（可能是嵌套的）都存在它所属的 `TraceThreadContext` 里。

除了上述层级之外，每个 slice 还会通过 Span.add_link() 记录它的前一个 slice，用来追踪执行流转。
