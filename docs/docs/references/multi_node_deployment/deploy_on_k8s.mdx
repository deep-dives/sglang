本文介绍如何在 Kubernetes（K8S）集群上，基于 RoCE 网络部署一个两节点的 SGLang 推理服务。

[LeaderWorkerSet（LWS）](https://github.com/kubernetes-sigs/lws) 是一个 Kubernetes API，用于解决 AI/ML 推理工作负载常见的部署模式问题。它最主要的应用场景就是多主机/多节点的分布式推理。

SGLang 也可以借助 LWS 部署在 Kubernetes 上，实现分布式模型服务。

<Note>
💡 AI Infra 学习笔记：LeaderWorkerSet（LWS）是 Kubernetes 社区为「1 个 leader + N 个 worker」这类分布式推理负载设计的 API：leader 负责对外入口与探活，worker 与 leader 同组共享生命周期。它天然适合 SGLang 多节点 TP 推理——`LWS_LEADER_ADDRESS`、`LWS_WORKER_INDEX` 等环境变量由控制器自动注入，省去手工指定节点地址。
</Note>

关于用 LWS 在 Kubernetes 上部署 SGLang 的更多细节，请参考本指南。

这里以 DeepSeek-R1 的部署为例。

## 前置条件

1. 至少需要两个 Kubernetes 节点，每个节点配备两套 H20 系统和八块 GPU。

2. 请确保你的 K8S 集群已正确安装 LWS。如果还没装，请按照[安装说明](https://lws.sigs.k8s.io/docs/installation/)操作。**注意：** 对于 LWS 版本 ≤0.5.x，你需要用 Downward API 获取 `LWS_WORKER_INDEX`，因为该特性的原生支持从 v0.6.0 才引入。

## 基础示例

基础示例文档请参考[在 GPU 上用 SGLang 与 LWS 部署分布式推理服务](https://github.com/kubernetes-sigs/lws/tree/main/docs/examples/sglang)。

不过，那份文档只覆盖了基础的 NCCL socket 模式。

本节中，我们会做一些简单修改，让这套配置适配 RDMA 场景。

* 准备用于在 k8s 上部署的 `lws.yaml` 文件。

```yaml Config
apiVersion: leaderworkerset.x-k8s.io/v1
kind: LeaderWorkerSet
metadata:
  name: sglang
spec:
  replicas: 1
  leaderWorkerTemplate:
    size: 2
    restartPolicy: RecreateGroupOnPodRestart
    leaderTemplate:
      metadata:
        labels:
          role: leader
      spec:
        dnsPolicy: ClusterFirstWithHostNet
        hostNetwork: true
        hostIPC: true
        containers:
          - name: sglang-leader
            image: sglang:latest
            securityContext:
              privileged: true
            env:
              - name: NCCL_IB_GID_INDEX
                value: "3"
            command:
              - python3
              - -m
              - sglang.launch_server
              - --model-path
              - /work/models
              - --mem-fraction-static
              -  "0.93"
              - --torch-compile-max-bs
              - "8"
              - --max-running-requests
              - "20"
              - --tp
              - "16" # Size of Tensor Parallelism
              - --dist-init-addr
              - $(LWS_LEADER_ADDRESS):20000
              - --nnodes
              - $(LWS_GROUP_SIZE)
              - --node-rank
              - $(LWS_WORKER_INDEX)
              - --trust-remote-code
              - --host
              - "0.0.0.0"
              - --port

              limits:
                nvidia.com/gpu: "8"
```

### 调试

* 设置 `NCCL_DEBUG=TRACE`，排查是否是 NCCL 通信问题。

这应该能解决大部分 NCCL 相关问题。

***注意：如果你发现容器环境下 `NCCL_DEBUG=TRACE` 不生效，而进程卡住或遇到难以诊断的问题，请尝试更换容器镜像。有些镜像可能没有正确处理标准错误输出。***

#### RoCE 场景

<Note>
💡 AI Infra 学习笔记：多节点 TP 推理的瓶颈通常是节点间通信。RoCE（RDMA over Converged Ethernet）是 NVIDIA GPU 集群常用的低延迟网络方案：配合 Mellanox 网卡与 OFED 驱动，让 NCCL 通信从 TCP socket 切换到 RDMA，可显著降低跨节点通信延迟。部署里大量出现的 `NCCL_IB_*`、`NVSHMEM_*` 环境变量，就是在控制 RDMA 的 HCA 选择、GID 与流量分类。
</Note>

* 请确保集群环境中可用的 RDMA 设备。
* 请确保集群节点配备了支持 RoCE 的 Mellanox 网卡。本例使用的是 Mellanox ConnectX 5 系列网卡，并已安装相应的 OFED 驱动。如果还没装，请参考[安装 OFED 驱动](https://docs.nvidia.com/networking/display/mlnxofedv24102180lts/installing+the+driver)文档进行安装。

## 成功的关键

* 在上面的 YAML 配置中，注意 NCCL 环境变量。对于旧版本的 NCCL，你需要检查 NCCL_IB_GID_INDEX 这个环境设置。
* NCCL_SOCKET_IFNAME 同样很关键，不过在容器化环境下通常不会出问题。
* 某些情况下还需要正确配置 GLOO_SOCKET_IFNAME。
* NCCL_DEBUG 对排查问题至关重要，但我发现有时它在容器内不会输出错误日志，这可能与所用 Docker 镜像有关。必要时可以试试更换镜像。
* 避免使用基于 Ubuntu 18.04 的 Docker 镜像，它们通常存在兼容性问题。

## 遗留问题

* 在 Kubernetes、Docker 或 Containerd 环境中，我们使用 hostNetwork 以避免性能下降。
* 我们使用了 privileged 模式，这并不安全。另外，在容器化环境中无法实现完全的 GPU 隔离。
