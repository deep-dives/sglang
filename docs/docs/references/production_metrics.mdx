## 配置指南

本节介绍如何搭建 `examples/monitoring` 目录里自带的监控栈（Prometheus + Grafana）。

### 前置条件

- 已安装 Docker 和 Docker Compose
- SGLang 服务器已开启指标

### 使用步骤

1.  **用开启指标的方式启动你的 SGLang 服务器：**

    ```bash Command
    python -m sglang.launch_server \
      --model-path <your_model_path> \
      --port 30000 \
      --enable-metrics \
      --enable-mfu-metrics
    ```
    把 `<your_model_path>` 换成你模型的实际路径（例如 `meta-llama/Meta-Llama-3.1-8B-Instruct`）。确保监控栈能访问到服务器（如果跑在 Docker 里，可能需要 `--host 0.0.0.0`）。默认情况下，指标端点位于 `http://<sglang_server_host>:30000/metrics`。

2.  **进入监控示例目录：**
    ```bash Command
    cd examples/monitoring
    ```

3.  **启动监控栈：**
    ```bash Command
    docker compose up -d
    ```
    这条命令会在后台启动 Prometheus 和 Grafana。

4.  **访问监控界面：**
    *   **Grafana：** 打开浏览器访问 [http://localhost:3000](http://localhost:3000)。
    *   **Prometheus：** 打开浏览器访问 [http://localhost:9090](http://localhost:9090)。

5.  **登录 Grafana：**
    *   默认用户名：`admin`
    *   默认密码：`admin`
    首次登录时会提示你修改密码。

6.  **查看面板：**
    SGLang 面板已预先配置好，通常会自动出现。依次进入 `Dashboards` -> `Browse` -> `SGLang Monitoring` 文件夹 -> `SGLang Dashboard`。

### 故障排查

*   **端口冲突：** 如果遇到类似 “port is already allocated” 的错误，先检查是否有其它服务（包括之前启动的 Prometheus/Grafana 实例）占用了 `9090` 或 `3000` 端口。用 `docker ps` 查看运行中的容器，用 `docker stop <container_id>` 停止它们，或用 `lsof -i :<port>` 找出占用端口的其它进程。如果这些端口与你系统上的必要服务长期冲突，可能需要在 `docker-compose.yaml` 里调整端口。

要在 Docker Compose 文件里把 Grafana 端口改成其它值（比如 3090），需要显式指定 grafana 服务下的端口映射。

    方案一：在 environment 段加上 GF_SERVER_HTTP_PORT：
    ```
      environment:
    - GF_AUTH_ANONYMOUS_ENABLED=true
    - GF_SERVER_HTTP_PORT=3090  # <-- Add this line
    ```
    方案二：使用端口映射：
    ```
    grafana:
      image: grafana/grafana:latest
      container_name: grafana
      ports:
      - "3090:3000"  # <-- Host:Container port mapping
    ```
*   **连接问题：**
    *   确认 Prometheus 和 Grafana 容器都在运行（`docker ps`）。
    *   检查 Grafana 中的 Prometheus 数据源配置（通常通过 `grafana/datasources/datasource.yaml` 自动配置）。进入 `Connections` -> `Data sources` -> `Prometheus`，URL 应指向 Prometheus 服务（例如 `http://prometheus:9090`）。
    *   确认 SGLang 服务器正在运行，且 *Prometheus 容器内部*能访问到指标端点（`http://<sglang_server_host>:30000/metrics`）。如果 SGLang 跑在宿主机上而 Prometheus 在 Docker 里，在 `prometheus.yaml` 的抓取配置中应使用 `host.docker.internal`（Docker Desktop）或你机器的网络 IP，而不是 `localhost`。
*   **面板上没有数据：**
    *   给你的 SGLang 服务器制造一些流量来产生指标。例如运行一次基准测试：
        ```bash Command
        python3 -m sglang.bench_serving --backend sglang --dataset-name random --num-prompts 100 --random-input 128 --random-output 128
        ```
    *   在 Prometheus 界面（`http://localhost:9090`）的 `Status` -> `Targets` 下查看 SGLang 端点是否被抓取成功。
    *   确认 Prometheus 指标中的 `model_name` 和 `instance` 标签与 Grafana 面板里用到的变量一致。可能需要在 Grafana 面板中调整变量，或在 Prometheus 配置里调整标签。

### 配置文件

监控配置由 `examples/monitoring` 目录下的以下文件定义：

*   `docker-compose.yaml`：定义 Prometheus 和 Grafana 服务。
*   `prometheus.yaml`：Prometheus 配置，包括抓取目标。
*   `grafana/datasources/datasource.yaml`：为 Grafana 配置 Prometheus 数据源。
*   `grafana/dashboards/config/dashboard.yaml`：告诉 Grafana 从指定路径加载面板。
*   `grafana/dashboards/json/sglang-dashboard.json`：实际的 Grafana 面板定义（JSON 格式）。

你可以通过修改这些文件来自定义配置。例如，如果 SGLang 服务器运行在不同主机或端口，可能需要更新 `prometheus.yaml` 中的 `static_configs` 目标。

💡 AI Infra 学习笔记：MFU（Model FLOPs Utilization，模型算力利用率）衡量 GPU 算力被实际用掉的比例，是判断推理引擎“把硬件榨干多少”的核心指标。SGLang 用预估计数器近似 MFU——用预估 FLOPs 除以理论峰值，加上读写字节数还能估算内存带宽利用。它不是硬件计数器，但足够用来做趋势分析和横向对比，排查“GPU 算力吃不满”（可能卡在内存带宽或调度开销）这类典型问题。
</Note>

## 预估性能指标（MFU 相关）

SGLang 导出以下按 GPU 计的预估计数器，可用于推导模型算力利用率（Model FLOPs Utilization，MFU）相关的信号：

- `sglang:estimated_flops_per_gpu_total`：预估的浮点运算量。
- `sglang:estimated_read_bytes_per_gpu_total`：预估的内存读取字节数。
- `sglang:estimated_write_bytes_per_gpu_total`：预估的内存写入字节数。

同时启用 `--enable-metrics` 和 `--enable-mfu-metrics` 时，这些指标才会可用。

这些是累计计数器，用 Prometheus 的 `rate(...)` 函数可以得到每秒的值。

### PromQL 示例

每张 GPU 的平均 TFLOPS：

```promql
rate(sglang:estimated_flops_per_gpu_total[1m]) / 1e12
```

平均预估内存带宽（GB/s）：

```promql
(rate(sglang:estimated_read_bytes_per_gpu_total[1m]) +
 rate(sglang:estimated_write_bytes_per_gpu_total[1m])) / 1e9
```

### 说明

- 这些指标是估算值，用于可观测性和趋势分析。
- 预估的内存字节反映的是建模流量，并非 GPU profiler 直接给出的硬件计数器。
