    description: "使用分片 CUDA 图（Piecewise CUDA Graph）降低预填充与扩展（extend）阶段的 kernel 启动开销，同时支持动态 token 形状。"
---

## 动机

标准 CUDA 图把整个模型前向过程捕获成一张图。这对解码（固定批大小）很有效，但对扩展/预填充阶段不适用，因为那里的 token 数量会随迭代而变化。

分片 CUDA 图（PCG）通过把模型的计算图在「切分点」（例如 MoE 的 dispatch 算子）处切成片段（大致每层一片）来解决这个问题。每个片段针对一组预定义的 token 长度分别捕获为一张 CUDA 图。运行时，输入被补齐到最近的已捕获大小，然后逐片重放。这样在仍然支持动态形状的同时，消除了预填充/扩展阶段的 kernel 启动开销。

<Note>
💡 AI Infra 学习笔记：预填充（prefill）与解码的 CUDA 图策略完全不同：解码批大小固定、可以整图捕获，而预填充的 token 数随请求变化，标准 CUDA 图无法直接套用。分片 CUDA 图（PCG）的思路是「把模型切成段，按一组预定义的 token 长度分别捕获，运行时向上取整补齐后重放」——用少量显存换取 kernel 启动开销的下降，同时保留动态形状能力。这是「形状固定 vs 动态」这一 CUDA 图核心矛盾的典型解法。
</Note>

最近我们**默认启用了 PCG**，这意味着旧的 `--enable-piecewise-cuda-graph` 参数已弃用。用 `--disable-piecewise-cuda-graph` 关闭它。

## 使用方法

在受支持的配置下，PCG 默认启用，无需额外参数：

```bash
python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct
```

### 关闭 PCG

```bash
python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --disable-piecewise-cuda-graph
```

### 自定义捕获大小

```bash
python3 -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --piecewise-cuda-graph-max-tokens 2048
```

## 问题反馈

PCG 默认启用但仍处于实验阶段。由于 PCG 依赖 `torch.compile` 追踪模型的前向过程，大多数 bug 来自 torch.compile 追踪失败（例如不可追踪的算子、动态控制流或图断点）。如果遇到与 PCG 相关的问题，请在启动命令中加上 `--disable-piecewise-cuda-graph` 关闭它，并在 [GitHub Issues](https://github.com/sgl-project/sglang/issues/new/choose) 反馈。非常感谢你帮助改进这一特性。

### 面向用户

如果在服务端启动时看到类似下面的报错，那是一个 PCG 的 bug：

```
Piecewise CUDA Graph is enabled by default as an experimental feature.
To work around this error, add --disable-piecewise-cuda-graph to your launch command.
Please report this issue at https://github.com/sgl-project/sglang/issues/new/choose
```

要绕过它，在启动命令中加上 `--disable-piecewise-cuda-graph`。提交 bug 报告时请包含：

1. 完整的错误堆栈
2. 模型名称与量化方法
3. 带全部参数的启动命令
4. GPU 型号与驱动版本

### 面向开发者

由于 PCG 依赖 `torch.compile` 追踪模型的前向过程，新开发的 CUDA kernel（包括 JIT kernel 和 sgl-kernels）通常无法直接与 `torch.compile` 兼容。追踪会在不可追踪的操作上失败，例如 kernel 内部的 JIT 编译、文件 I/O 或动态模块加载。

要让 kernel 与 PCG 兼容，需要用 `sglang.srt.utils.custom_op` 中的 `register_custom_op` 把它注册为自定义算子。这会把 kernel 包装成编译图中的不透明节点，使 `torch.compile` 不会追踪其内部。

**示例用法（JIT kernel）：**

```python
from sglang.srt.utils.custom_op import register_custom_op

# Inplace operator (no return value)
@register_custom_op(mutates_args=["output_q", "output_s"])
def per_token_group_quant_8bit(
    input: torch.Tensor,
    output_q: torch.Tensor,
    output_s: torch.Tensor,
) -> None:
    # kernel implementation ...
```

**示例用法（带输出的算子）：**

```python
# out_shape indicates which argument has the same shape as the output
@register_custom_op(mutates_args=["x"], out_shape=0)
def add(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    return x.add_(y)
```

如需包装外部库函数（例如 FlashInfer kernel），改用 `register_custom_op_from_extern`。完整 API 文档参见 `python/sglang/srt/utils/custom_op.py`。

## 工作原理

### Torch compile 后端

PCG 使用带自定义后端（`SGLangBackend`）的 `torch.compile` 来切分并编译模型的前向过程。流程如下：

```
model.forward wrapper
→ torch.compile(..., backend=SGLangBackend)
→ FX graph
→ split_graph() at registered split ops
→ split_gm (top-level graph that chains the pieces)
→ replace capturable submodules with CUDAPiecewiseBackend
→ runtime dispatch: eager split ops + per-piece capture/replay
```

<Note>
💡 AI Infra 学习笔记：PCG 与 torch.compile 深度绑定：它用 Dynamo 把模型前向变成 FX 图，在切分点切开，再逐段编译+捕获。这意味着新增 kernel 必须用 `register_custom_op` 包装成不透明节点才能兼容——这是推理引擎接入编译器的通用工程模式：把「编译器看不懂的自研 kernel」藏进自定义算子，避免追踪失败。
</Note>

- **安装**：`install_torch_compiled()` 用包装函数替换 `model.forward`。当 `is_in_piecewise_cuda_graph()` 返回 True 时，包装器分发到编译后的可调用对象；否则回退到原始 forward。第一次通过该路径调用会触发 Dynamo 追踪和图编译——CUDA 图重放只在捕获阶段完成后才发生。
- **切分**：当 `torch.compile` 追踪模型时，`SGLangBackend` 收到 FX 图并调用 `split_graph()`。`CompilationConfig.split_ops` 中列出的算子被当作切分点，图在每处被切开。这些切分算子子模块在运行时保持 eager 执行，而周围的子模块被编译并由 `CUDAPiecewiseBackend` 包装。结果是顶层「缝合图」（`split_gm`），其子节点如 `submod_0`、`submod_1`、……交替穿插着可捕获子图和 eager 的切分算子子模块。
- **替换**：`PiecewiseCompileInterpreter` 遍历 `split_gm` 中每个可捕获子模块，为其按通用（动态）形状编译，并原地替换为 `CUDAPiecewiseBackend` 实例。切分算子子模块（例如注意力、all-reduce）保持原样，运行时以 eager 方式执行。
- **分发**：运行时，调用 `split_gm` 会执行缝合图，按顺序调用每个子模块。切分算子子模块以 eager 方式运行。每个 `CUDAPiecewiseBackend` 子模块经历三个阶段：
  - **编译预热**——运行通用形状的编译路径。
  - **捕获**——对每个捕获大小，先跑一次预热，再录制一张 CUDA 图。
  - **稳态重放**——每次前向都重放捕获的 CUDA 图。

### 分片 CUDA 图 runner

`PiecewiseCudaGraphRunner` 通过三个阶段编排完整生命周期：

- **编译**——先用一次虚拟前向预热 JIT kernel，再用 `torch.compile` 包装模型，触发 Dynamo 追踪来切分 FX 图，并为每个子图片段创建 `CUDAPiecewiseBackend` 实例。
- **捕获**——按倒序（从大到小）遍历捕获大小。对每个大小，前向运行两次（一次预热、一次 CUDA 图捕获）。
- **重放**——运行时，通过二分查找找到 >= 实际 token 数的最小已捕获大小，把输入用零填充拷入静态缓冲区，重放捕获的 CUDA 图，再把输出切回实际 token 数。

### 内存优化

PCG 的内存开销来自两部分：**torch 内存分配器**和**非 torch 内存**。

得益于多项优化，torch 内存分配器的开销可以忽略：全局共享内存池在所有 CUDA 图 runner 和捕获大小之间复用；捕获按倒序（从大到小）进行，较小的图会复用较大图分配的内存；最后一个子图的输出 tensor 以弱引用保存，以最大化内存复用。

主要的内存开销来自非 torch 内存——CUDA 图对象本身需要 GPU 显存来存储录制的 kernel 启动参数和内部状态。该开销随捕获大小数量增长，这也是 `piecewise_cuda_graph_max_tokens` 默认被保守封顶的原因。

### 形状配置

分片 CUDA 图为一组 token 数量预先捕获图。运行时，实际 token 数向上取整到最近的已捕获大小（通过二分查找），并重放对应的图。如果 token 数超过最大的已捕获大小，运行时回退到普通（非图）前向路径。

## 兼容性

PCG 在以下场景会被自动禁用。我们正在积极扩展兼容性——其中许多很快会得到支持。

- 已禁用的模型架构（如 `DeepseekV32ForCausalLM`）
- 投机解码
- DP 注意力
- 流水线并行（`pp_size > 1`）
- 非 CUDA 硬件（AMD ROCm、Ascend NPU）
- MoE A2A 后端
- LoRA
- 多模态 / VLM 模型
- DLLM（扩散 LLM）
- 确定性推理
- PD 分离部署
- 专家分布记录器 / EPLB

用 `--enforce-piecewise-cuda-graph` 跳过所有自动禁用检查（仅供测试/调试）。
