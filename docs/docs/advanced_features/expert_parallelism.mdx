SGLang 中的专家并行（EP）把混合专家（MoE）模型中的专家权重分布到多块设备上，解决内存瓶颈并实现高性能推理的高效扩展。它对服务大规模 MoE 模型尤其重要——这类模型中，token 会被动态路由到分布在多块 GPU 上的专门专家。借助优化的 all-to-all 通信和分组矩阵乘法（GEMM），EP 能降低延迟、提升吞吐并最小化 GPU 空闲时间。SGLang 的 EP 通过模块化框架提供很强的可扩展性，可以在不改动核心逻辑的前提下无缝集成自定义 kernel、后端和优化，支持多种硬件与量化方案。

<Note>
💡 AI Infra 学习笔记：专家并行（EP）解决的是 MoE 模型的两个问题：一是权重放不下——几百个专家里只有一部分被激活，没必要复制到每块 GPU；二是负载不均衡——不同 token 路由到不同专家，各 GPU 上专家的工作量差异大。EP 把专家按需分布到各设备，token 通过 all-to-all 通信「分发-计算-回收」（dispatch-combine），配合分组 GEMM 提升矩阵计算的批量效率。EP 与 TP 的核心区别：TP 切分单个算子的权重、每个算子都要通信；EP 只切分专家，通信只在 MoE 层发生一次。
</Note>


## 支持的后端与选择指引

SGLang 的 EP 为不同场景集成了多样且高效的后端，允许对性能权衡做细粒度控制。用户通过命令行参数指定后端：
- `--moe-a2a-backend`：选择 all-to-all 通信的后端。
- `--moe-runner-backend`：选择 MoE 计算的后端。

DeepEP 和 Mooncake 后端支持两种 token 分发模式：`normal` 模式（为高吞吐的预填充工作负载优化）和 `low_latency` 模式（为低延迟、兼容 CUDA 图的解码工作负载优化）。MORI 后端目前只支持 `normal` 模式。NIXL-EP 和 PPLX 目前在低延迟模式下运行并支持 CUDA 图（PPLX 复用 DeepEP 的低延迟 masked 专家计算路径）。建议用户设置 `--deepep-mode auto`，让运行时自动切换分发模式。设置 `--deepep-mode normal` 或 `--deepep-mode low_latency` 则适合调试或开发。

目前，DeepEP、Mooncake、NIXL-EP、`ascend_fuseep`、`pplx` 和 MORI 只支持 `ep_size = tp_size` 的情况。对于 EP 与 TP 混合（即 `ep_size < tp_size`），只支持 `none` 后端（基于 All-Reduce 或 All-Gather 的分发）。注意 `pplx` 还需要 `--enable-dp-attention` 且至少有 2 个 DP 组（即 `tp_size / attention_tp_size > 1`）；否则无法构建 pplx-kernels 的 AllToAll。

## 可扩展的 EP 框架

SGLang 的 EP 框架提供模块化抽象，便于集成自定义 kernel、后端和优化。它把 MoE 前向过程解耦为多个阶段（dispatch → pre-permute → core runner → post-permute → combine），从而无需重构核心逻辑即可无缝扩展。

### 框架概览

框架以 `FusedMoE` 为核心，作为统一的、可扩展结构的入口。关键组件包括：
- **Dispatcher**：管理 DeepEP 等后端的分发/回收（实现 `BaseDispatcher` 子类）。
- **MoeRunner**：通过 `MoeRunnerCore` 实现（如 `TritonRunnerCore`）编排分组 GEMM 的执行。
- **PermuteMethodPool**：自动注册布局转换（例如动态模式下通过 `register_pre_permute` 和 `register_post_permute` 做 pre/post-permute，或用 `register_fused_func` 做静态的、兼容 torch.compile 的融合操作）。
- **TopK Router**：与后端无关的专家选择。

这种设计通过 `--moe-a2a-backend` 和 `--moe-runner-backend` 支持多个后端，量化则通过标准化的 `apply()` 方法集成。计算流程保证了模块化：

```text Output
[input_hidden_states]
          |
          v
     TopK.forward -> select_experts / triton_kernels.routing / bypass
          |
          v
     [TopKOutput]
          |
          v
   FusedMoE.forward -> Dispatcher.dispatch -> DeepEP / bypass
          |                     |
          |                     v
          |              [DispatchOutput]
          |                     |
          |                     v
          |             quant_method.apply -> MoeRunner.forward
          |                     |              |
          |                     |              v
          |                     | pre-permute + grouped_gemm + post-permute
          |                     |              |
          |                     |--------------
          |                     v
          |               [CombineInput]
          |                     |
          |                     v
          |            Dispatcher.combine -> DeepEP / bypass
          |                     |
          |---------------------
          v
[final_hidden_states]
```

更多细节参见 [MoE 重构路线图](https://github.com/sgl-project/sglang/issues/8715)。

### 实现新后端

要新增一个后端：
1. 对于新的 all-to-all 分发器，实现一个带 `dispatch` 和 `combine` 方法的 `BaseDispatcher` 子类。
2. 对于新的 MoE runner 后端，为核心操作（如分组 GEMM）定义一个 `MoeRunnerCore` 子类。
3. 为分发器或模型 runner 定义新的输入/输出格式（例如 `RunnerInput`、`RunnerOutput`）。
4. 注册 permute/unpermute 方法以保证兼容：
   - **Fused 模式**（静态、兼容 torch.compile）：用 `register_fused_func` 处理端到端操作。
   - **Permute 模式**（动态）：注册 `register_pre_permute` 和 `register_post_permute` 以支持灵活的布局。

完整改动参见 [MoE 重构实现 PR](https://github.com/sgl-project/sglang/pull/9269)，包括类型提示与配置扩展。

### 示例

示例实现参见 [moe_runner/triton.py](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/moe/moe_runner/triton.py)，它演示了带注册 fused 与 permute 函数的基于 Triton 的分组 GEMM。

## 计算与通信重叠

SGLang 的 EP 采用先进的重叠技术，把通信延迟隐藏在计算背后，最大化 MoE 层的 GPU 利用率。

<Note>
💡 AI Infra 学习笔记：EP 的性能关键在「通信与计算重叠」。MoE 层的 token 分发（all-to-all）要经过网络，如果等通信完再算，GPU 会空转。TBO 把请求拆成两个微批，让一批的注意力计算与另一批的分发/回收通信交错；SBO 则让单个批内的共享专家计算与通信重叠。理解「用计算掩盖通信」是分布式推理优化的核心思路，也是面试高频考点。
</Note>


### 双批重叠（TBO）

TBO 把请求拆成微批次，把注意力计算与分发/回收操作交错执行。执行图中的让出点（yield point）允许暂停以进行重叠，从而在不引起峰值内存飙升的情况下提升整体吞吐：

```python Example
operations = [
    self._forward_attn,
    YieldOperation(),  # Overlap with dispatch of prior micro-batch
    self._forward_dispatch,
    self._forward_mlp,
    YieldOperation(),  # Overlap with combine
    self._forward_combine,
]
```

用户需要指定 `--enable-two-batch-overlap` 才能解锁最高 2 倍的吞吐。更多细节参见[大规模 EP 博客](https://lmsys.org/blog/2025-05-05-large-scale-ep/#two-batch-overlap)。

### 单批重叠（SBO）

SGLang 为单批重叠（SBO）引入了一套分发器钩子系统，可以在单个批内实现操作重叠——例如共享专家计算与通信重叠——同时把逻辑分散化以增强模块性。这些钩子在 `dispatch` 和 `combine` 操作前后执行，无需修改核心 MoE 模块。这种设计简化了接口、降低了耦合、提升了可扩展性。实现细节以及共享专家与 DeepEP combine 操作重叠的示例，参见 [PR #13327](https://github.com/sgl-project/sglang/pull/13327)。用户可设置 `--enable-single-batch-overlap` 启用该特性。


## 工作负载均衡器

SGLang 集成了 DeepSeek 的[专家并行负载均衡器（EPLB）](https://github.com/deepseek-ai/EPLB)，用于解决 MoE 模型中的路由不均衡问题。通过分析专家激活统计，EPLB 计算出最优的专家排布，策略性地放置或复制专家，以最小化 GPU 利用率方差、减少空闲周期并增强可扩展性。

启用 EPLB 使用参数 `--enable-eplb`。为了最佳性能，增大批大小以稳定激活统计，并配置周期性再均衡（例如每 1000 个请求）以适应不断变化的工作负载。模拟表明，负载均衡度（平均计算时间与最大计算时间之比）有显著提升，且与吞吐增益强相关。

更多细节参见[大规模 EP 博客中的 EPLB 一节](https://lmsys.org/blog/2025-05-05-large-scale-ep/#expert-parallelism-load-balancer)和 [EPLB 仓库](https://github.com/deepseek-ai/eplb)。


## Ascend NPU 指南
### Ascend NPU 上 SGLang 配置指南
- `--moe-a2a-backend` 仅支持 `deepep` 和 `ascend_fuseep` 后端，

    - `deepep`：机制与上述描述一致。

    - `ascend_fuseep`：提供一个大型融合算子，把 dispatch 与 combine 之间的所有操作整合起来以加速 MoE 计算。仅在 PD 分离模式的解码阶段使用。

- `--moe-runner-backend` 参数无需配置。

- `--deepep-mode`：

    - 在 PD 混合模式下，请设置 `--deepep-mode auto`。

    - 在 PD 分离模式下，预填充实例设置 `--deepep-mode normal`，解码实例设置 `--deepep-mode low_latency`。

### DeepEP Ascend 介绍
DeepEP Ascend 是 DeepEP 通信库面向华为 Ascend NPU 的适配版本，专为混合专家（MoE）模型的专家并行（EP）设计。
它支持「蚂蚁搬家」函数（把序列长度拆成多轮，做流式分批传输），以优化预填充阶段集体通信占用的缓冲区大小，尤其适用于长序列。

可以通过以下环境变量在分发与回收两个阶段启用「蚂蚁搬家」函数：

- `DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS`：在分发阶段启用蚂蚁搬家函数。表示每个 rank 每轮传输的 token 数，默认 8192。

- `DEEPEP_NORMAL_LONG_SEQ_ROUND`：在分发阶段启用蚂蚁搬家函数。表示每个 rank 传输的轮数，默认 1。

- `DEEPEP_NORMAL_COMBINE_ENABLE_LONG_SEQ`：在回收阶段启用蚂蚁搬家函数，默认 0（表示禁用）。

`DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS * DEEPEP_NORMAL_LONG_SEQ_ROUND` 即输入序列长度。当输入序列长度超过 8192 时，建议在分发和回收两个阶段都启用蚂蚁搬家函数。

环境变量 `HCCL_BUFFSIZE` 用于配置实际分配的缓冲区大小（MB）。其计算公式如下：
```text Output
# Enable Ant-moving Function
HCCL_BUFFSIZE >= 2 * (102MB + 4MB + DEEPEP_NORMAL_LONG_SEQ_PER_ROUND_TOKENS * (hidden_size + hidden_size + hidden_size) * topk) + PADDING_BUFFSIZE

# Disable Ant-moving Function
HCCL_BUFFSIZE >= 2 * (102MB + 4MB + TOTAL_SEQ_LEN * (hidden_size + hidden_size) * topk) + PADDING_BUFFSIZE
```
其中各参数说明如下：

- `hidden_size`：模型配置中的隐藏层大小。

- `topk`：选中的路由专家数量。

- `TOTAL_SEQ_LEN`：输入序列长度。

- `PADDING_BUFFSIZE`：建议取值 20 或更大。
