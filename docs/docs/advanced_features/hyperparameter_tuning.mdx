## 提升离线批量推理的吞吐量

在离线批量推理中，追求高吞吐最重要的一点是把批大小（batch size）做大。
当服务端处于满负载的稳态运行时，请在日志中关注以下内容：

```text Output
Decode batch. #running-req: 233, #token: 370959, token usage: 0.82, cuda graph: True, gen throughput (token/s): 4594.01, #queue-req: 317
```

<Note>
💡 AI Infra 学习笔记：这行日志是理解推理引擎运行状态的"仪表盘"——`#running-req` 是当前并行解码的请求数，`token usage` 是 KV 缓存利用率，`gen throughput` 是生成吞吐，`#queue-req` 是排队中的请求数。调优离线批量推理时，先读懂这几项指标，比盲目改参数更有效。
</Note>

### 调整请求提交速度来控制 `#queue-req`

`#queue-req` 表示队列中请求的数量。
如果你经常看到 `#queue-req: 0`，说明你的客户端代码提交请求的速度太慢了。
`#queue-req` 的健康区间是 `100 - 2000`。
但也要避免 `#queue-req` 过大，否则会增加服务端的调度开销。

### 让 `token usage` 保持高位

`token usage` 表示服务端 KV 缓存内存的利用率。`token usage > 0.9` 说明利用率良好。

如果你经常看到 `token usage < 0.9` 且 `#queue-req > 0`，说明服务端在接收新请求时过于保守。你可以把 `--schedule-conservativeness` 调低，例如 0.3。
服务端过于保守的情况，通常出现在用户提交了大量 `max_new_tokens` 很大的请求、但这些请求又因 EOS 或停止字符串而提前结束时。

另一方面，如果你看到 `token usage` 非常高，并且经常出现类似
`KV cache pool is full. Retract requests. #retracted_reqs: 1, #new_token_ratio: 0.9998 -> 1.0000` 的警告，可以把 `--schedule-conservativeness` 调高到 1.3 之类的值。
如果 `KV cache pool is full. Retract requests.` 只是偶尔出现（大约每分钟一次），那没有问题。

### 调整 `--mem-fraction-static` 来扩大 KV 缓存池容量
SGLang 按以下方式分配内存：

总内存占用 = 模型权重 + KV 缓存池 + CUDA 图缓冲区 + 激活值

`--mem-fraction-static` 参数决定了前两项能分到多少内存：

mem_fraction_static = (模型权重 + KV 缓存池) / GPU 显存容量

要支撑更高的并发，你应该尽可能把 `--mem-fraction-static` 调高、从而最大化 KV 缓存池容量，同时仍要为激活值和 CUDA 图缓冲区预留足够内存。

<Note>
💡 AI Infra 学习笔记：`--mem-fraction-static` 决定了"模型权重 + KV 缓存池"占 GPU 显存的比例，是并发能力与稳定性的核心平衡点。调高它 = 更大的 KV 缓存池 = 能扛更多并发，但留给激活值和 CUDA 图缓冲的显存变少，容易 OOM。这是推理引擎里最常见的"压榨显存"调优，面试中也常被问到。
</Note>

SGLang 会用简单的启发式规则来设定 `--mem-fraction-static` 的默认值，但你可以针对自己的场景优化它。
经验法则：为激活值预留 5–8 GB 内存通常就足够了。你可以在服务端即将就绪时检查日志来确认这一点。
留意类似下面的日志：

```text Output
[2025-08-11 17:17:03] max_total_num_tokens=665690, chunked_prefill_size=8192, max_prefill_tokens=16384, max_running_requests=4096, context_len=65536, available_gpu_mem=13.50 GB
```

检查 `available_gpu_mem` 的值。
- 如果它在 5–8 GB 之间，说明设置是合适的。
- 如果太高（例如 10 - 20 GB），调高 `--mem-fraction-static`，把更多内存分配给 KV 缓存。
- 如果太低，后续可能会遇到内存不足（OOM）错误，所以请调低 `--mem-fraction-static`。

另一个直接的方法是：把 `--mem-fraction-static` 每次增加 0.01，直到你的工作负载出现 OOM 错误为止。

### 通过调整 `--chunked-prefill-size`、`--mem-fraction-static` 和 `--max-running-requests` 来避免 OOM

如果遇到内存不足（OOM）错误，可以调整以下参数：

- 如果 OOM 发生在预填充阶段，试着把 `--chunked-prefill-size` 降到 `4096` 或 `2048`。这会节省内存，但会拖慢长提示词的预填充速度。
- 如果 OOM 发生在解码阶段，试着调低 `--max-running-requests`。
- 也可以把 `--mem-fraction-static` 调小，例如 0.8 或 0.7。这会降低 KV 缓存内存池的内存占用，有助于避免预填充和解码阶段的 OOM。但代价是限制最大并发数、降低峰值吞吐。

### 调整 `--cuda-graph-max-bs-decode`
默认情况下，CUDA 图只在小批大小时启用（例如小于 160 或 256）。
但对于某些模型，尤其是在张量并行规模较大时，CUDA 图在批大小达到 512 或 768 时依然有用。
因此，把 `--cuda-graph-max-bs-decode` 调大一些可能是有益的。
注意 CUDA 图会占用更多内存，所以你可能需要同时调低 `--mem-fraction-static`。

<Note>
💡 AI Infra 学习笔记：CUDA 图把一段 GPU kernel 启动序列"录制"成一张图，之后整体重放，可以省掉大量 kernel 启动开销。它只对小批大小效果明显（大批大小下计算本身已成瓶颈），但会额外占用显存——这就是为什么调大 `--cuda-graph-max-bs-decode` 往往需要同步调低 `--mem-fraction-static`。
</Note>

### 调整 `--dp-size` 和 `--tp-size`

数据并行（data parallelism）更利于提升吞吐。当 GPU 显存充足时，追求吞吐应优先考虑数据并行。要获得比 `dp_size` 参数更好的数据并行方案，请参考 [SGLang Model Gateway（原 Router）](../advanced_features/sgl_model_gateway)。

### 其他可选项

- `torch.compile` 能加速小模型在小批大小下的推理。你可以用 `--enable-torch-compile` 启用它。
- 尝试其他量化方案（例如用 `--quantization fp8` 做 FP8 量化）。
- 尝试其他并行策略（例如 [专家并行](https://lmsys.org/blog/2025-05-05-large-scale-ep/)），或对 deepseek 模型使用 DP attention（`--enable-dp-attention --dp-size 8`）。
- 如果负载中有大量共享前缀，试试 `--schedule-policy lpm`。这里的 `lpm` 表示最长前缀匹配（longest prefix match），它会重排请求以促进缓存命中，但会引入更多调度开销。
