本指南解释数据并行（DP）与数据并行注意力（DPA）的区别、如何正确启用每种模式，以及如何使用 SGLang Model Gateway（SMG）做生产级 DP 部署。

## 数据并行（DP）

**数据并行（DP）** 是最常见的并行策略：把整个模型复制到多组 GPU 上，并行处理不同的请求批次。每组 GPU 处理独立的请求。配合合适的路由策略——稍后我们会介绍 SGLang Model Gateway 中的路由算法——你的推理系统吞吐量几乎可以线性倍增。

### 关键特征

- 每个副本都有模型的完整拷贝
- 请求被分发/分散到各个副本
- 单个请求推理期间副本之间无通信（简单 DP 下）

<Note>
💡 AI Infra 学习笔记：DP 是最直观的扩展方式——整模型复制、各副本处理不同请求、副本间无需通信，理论上吞吐随副本数近线性增长。它的收益高度依赖路由：如果路由能把「共享前缀」的请求送到同一副本，RadixAttention 命中率会非常高；乱路由则会让每个副本的缓存都无法命中。
</Note>


## 数据并行注意力（DPA）

**数据并行注意力（DPA）**，又称 DP Attention，是一种高级并行策略。DPA 对**多头潜在注意力（MLA）**模型（如 DeepSeek、MiniMax、Kimi-K2）的收益最大，但它也支持像 Qwen 这样的**标准注意力模型**。

### MLA 模型下张量并行的问题

推理中最常见的并行策略是**张量并行（TP）**。然而，TP 对某些模型可能不是最有效的策略。例如，DeepSeek 模型使用 MLA，且只有**一个 KV 头**。如果在 8 块 GPU 上使用张量并行，会导致：

- **KV 缓存在所有 GPU 上重复**
- **不必要的内存占用**限制了批大小
- 由于内存限制导致**吞吐下降**

<Note>
💡 AI Infra 学习笔记：MLA 模型只有一个 KV 头，TP 会把这份 KV 头切到多卡上，导致每个 rank 都存了一份重复的 KV 缓存——既浪费显存又限制批大小。DPA 的思路是「注意力不做 TP，而是让不同 DP 副本各自独立处理一批请求、各自持有自己的 KV 缓存」；MoE 层则配合 EP 分发专家。这样既消除了 KV 重复，又能把大批的注意力工作摊到多副本上。DPA 本质上是「把 TP 从注意力路径上撤下来、用 DP 补齐」的混合并行。
</Note>


### DPA 如何工作

DPA 通过**专门对注意力组件应用数据并行**来解决这些限制。

### DPA 的主要优势

1. **显著减少 KV 缓存内存**：每个 DP 副本只为自己批次的请求存储 KV 缓存
2. **更大的批大小**：内存节省带来了更大的批大小
3. **解码吞吐提升**：对基于 MLA 的模型有显著的吞吐增益
4. **独立的前向模式**：每个 DP 副本可以处于不同的前向模式（预填充、解码或空闲），并在注意力计算期间独立处理分配给它的批次

### DPA 与 MoE 的专家并行结合

对于 DeepSeek 这类 MoE 模型，DPA **通常**会与专家并行（EP）搭配，以获得大规模下的最佳吞吐。然而，**DPA 并不依赖 EP**：如果你的部署不需要专家分片，可以在不启用 EP 的情况下启用 DPA。

- 把 256+ 个专家权重分布到多块 GPU 上（无法装进单块 GPU）
- 通过 DeepEP 实现高效的 all-to-all token 路由
- 扩展到大规模集群（相比朴素 TP 最高 5 倍吞吐提升）

### DeepSeek 的推荐配置

```bash
python -m sglang.launch_server \
    --model-path deepseek-ai/DeepSeek-V3 \
    --tp 8 \
    --dp-size 8 \
    --ep 8 \
    --enable-dp-attention \
    --moe-a2a-backend deepep \
    --moe-runner-backend deep_gemm
```

> **注意**：使用 `--enable-dp-attention` 时必须显式设置 `--dp-size`。如果 `dp_size` 为 1（默认值），DPA 会被禁用。

EP 的详细配置（DeepEP、双批重叠、EPLB）参见[专家并行](/docs/advanced_features/expert_parallelism)。

### 支持的模型

DPA 支持以下模型架构：

- **MLA（多头潜在注意力）模型**——DPA 在此类模型上收益最大：
  - DeepSeek 系列（DeepSeek-V2、DeepSeek-V3、DeepSeek-R1）
  - MiniMax 模型
  - Kimi-K2
  - 其他使用 MLA 架构的模型

- **标准注意力模型**——同样支持：
  - Qwen 模型（参见 [PR #6121](https://github.com/sgl-project/sglang/pull/6121)）

对于 Llama 这类使用标准 GQA 的模型，通常推荐标准 DP 或 TP。

要启用 DPA，在服务端启动命令中加上 `--enable-dp-attention`。

### 激活逻辑

DPA 通过服务端参数（CLI 或配置）显式启用。你必须同时设置 `--dp-size` 和 `--enable-dp-attention`：

```bash
python -m sglang.launch_server \
    --model-path deepseek-ai/DeepSeek-V3 \
    --tp 8 \
    --dp-size 8 \
    --enable-dp-attention
```

**重要**：DPA 要生效，`--dp-size` 必须大于 1。当 `dp_size == 1`（默认值）时，`--enable-dp-attention` 会被自动禁用。还必须满足约束 `tp_size % dp_size == 0`。

### MLA 模型的标准 DP

注意，MLA 模型当然也支持 DP。假设你想为 MLA 模型启用标准 DP：首先，独立启动每个 MLA 模型的副本（可以逐个启动这些副本，并启用 DPA）。启动完所有副本后，启动一个 SMG，并把所有副本接入该 SMG。下面详细说明 SMG。

## 现代数据并行 SGLang Model Gateway（SMG）

### 原生 DP 模式

SGLang 的原生 DP（内置数据并行）在单个 SGLang 实例内创建多个 worker 进程，由 `DataParallelController` 控制，启动参数为 `dp-size`。

```bash
# Native DP mode
python -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --dp-size 4
```

**局限：**

- 仅内置进程内负载均衡（例如 `round_robin`、`total_requests`、`total_tokens`）
- 无缓存感知路由
- 可观测性与指标有限
- 无故障容错或熔断器
- 不适合生产工作负载

⚠️ 目前**强烈不建议**使用原生 DP。它只出现在一些古老/过时的 RL 框架中。你可以在任何场景下用 SGLang Model Gateway（SMG）来支撑你的数据并行。

<Note>
💡 AI Infra 学习笔记：DP 的路由质量决定缓存命中率。朴素 round-robin 会把共享前缀的请求散到不同副本，RadixAttention 的命中率随之崩溃；而 SMG 维护每个 worker 的近似前缀树，把请求路由到最可能已持有其前缀的副本。缓存感知路由把「集群级缓存命中率」变成路由策略的函数——这也是「路由」从简单负载均衡升级为性能优化手段的核心原因。
</Note>


### 基于 SMG 的 DP（推荐）

从 2024 年 9 月开始，SGLang Model Gateway（即 SMG，原名 SGLang DP Router）作为生产级的 DP 路由系统用 Rust 构建。它从 DP 路由起步，后来扩展到协调 RL、PD 分离部署等更多场景。本文档只讨论 SMG 在 DP 路由中的用法。其他用法请参考 [SGLang Model Gateway 文档](/docs/advanced_features/sgl_model_gateway)。

> 为了获得最佳的生产级路由性能并把开销压到极致，我们用 Rust 而非 Python 构建 SMG——Python 永远不够快。

**我们强烈推荐在生产级数据并行中使用 SGLang Model Gateway（SMG）。** 相比原生 DP 模式，SMG 有显著优势。

```bash
# SMG-based DP mode (Recommended)
python -m sglang_router.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --dp-size 4
```

⚠️ 注意：**SMG 与原生 DP 使用相同的启动参数 `--dp-size`**。但原生 DP 的入口是 `python -m sglang.launch_server`，SMG 的入口是 `python -m sglang_router.launch_server`。

### 各自的使用时机

**何时使用原生 DP：**

- ~永远不要用原生/朴素 DP~
- 学习 DP 路由的教材

**何时使用基于 SMG 的 DP：**

- 任何你认为需要 DP 的场合
- 生产环境部署
- 多节点分布式部署
- 带共享前缀的工作负载（高缓存复用潜力）
- 需要高可用与可靠性特性
- 需要详细的可观测性与指标
- 想要高效的 RL rollout 系统

注意，对于 RL rollout 系统，**有四个关键原因说明基于 SMG 的 DP 远优于朴素 DP 路由**。详情见 [RL 中的负载均衡路由器](/docs/advanced_features/sglang_for_rl#load-balancing-router)。

### SMG 快速上手

**安装**

```bash
pip install sglang-router
# or
pip install "sglang[all]"
```

**方式 A：同时启动 Worker 与 SMG（最简单）**

这是最容易上手的方式——SMG 与 worker 一起启动：

```bash
python -m sglang_router.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --dp-size 4 \
    --host 0.0.0.0 \
    --port 30000
```

**方式 B：分开启动（多节点）**

用于跨多台机器的分布式部署：

1. 在每个节点上启动 worker

```bash
# Node 1
python -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --port 8000

# Node 2
python -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --port 8000
```

2. 启动 SMG 并指向 worker

```bash
python -m sglang_router.launch_router \
    --worker-urls http://node1:8000 http://node2:8000 \
    --policy cache_aware \
    --host 0.0.0.0 \
    --port 30000
```

**方式 C：Worker 动态注册**

用于 worker 可动态增删的弹性部署：

```bash
# Launch SMG first
python -m sglang_router.launch_router \
    --policy cache_aware \
    --host 0.0.0.0 \
    --port 30000

# Register workers dynamically
curl -X POST http://localhost:30000/workers \
    -H "Content-Type: application/json" \
    -d '{"url": "http://worker1:8000"}'

curl -X POST http://localhost:30000/workers \
    -H "Content-Type: application/json" \
    -d '{"url": "http://worker2:8000"}'
```

**缓存感知策略（默认，推荐）**

缓存感知策略能为大多数工作负载提供最佳性能：

```bash
python -m sglang_router.launch_router \
    --worker-urls http://worker1:8000 http://worker2:8000 \
    --policy cache_aware \
    --cache-threshold 0.5 \
    --balance-abs-threshold 32 \
    --balance-rel-threshold 1.5 \
    --eviction-interval-secs 120 \
    --max-tree-size 67108864
```

**工作原理：**

1. 基于请求历史为每个 worker 维护一棵近似前缀树
2. 把请求路由到前缀匹配最高（缓存命中）的 worker
3. 负载不均衡时回退到最短队列路由
4. 自动淘汰旧条目以防止内存溢出

### 最佳实践

1. **从 `cache_aware` 策略开始**——它为大多数工作负载提供了缓存局部性与负载分布之间的最佳平衡
2. **生产环境用 SMG**——优先用 `sglang_router.launch_server` 而非 `sglang.launch_server`，以获得更好的可靠性与可观测性
3. **启用健康检查**——配置 `--router-health-check-interval-secs` 自动发现并剔除不健康的 worker

**套用最佳实践的推荐命令：**

```bash
python -m sglang_router.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --dp-size 4 \
    --router-policy cache_aware \
    --router-health-check-interval-secs 30 \
    --router-prometheus-port 10001 \
    --host 0.0.0.0 \
    --port 30000
```

高级配置（熔断器、重试、Prometheus 指标、K8s 集成）参见 [SGLang Model Gateway 文档](/docs/advanced_features/sgl_model_gateway)。
