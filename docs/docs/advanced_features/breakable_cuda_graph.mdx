## 动机

标准 CUDA 图会把整个前向过程捕获成一张不透明的图。这有利于性能，但带来两个问题：

1. **调试困难。** 当捕获的图内部出问题时（输出错误、数值不匹配、崩溃），由于图作为一个整体单元重放，你无法单步执行其中的操作，也无法插入打印语句。

2. **部分算子不兼容。** 某些操作——动态控制流、主机-设备同步、JIT 编译，或跨迭代行为变化的算子——根本无法被捕获进 CUDA 图。目前唯一的变通办法是完全禁用 CUDA 图，但这会牺牲模型其余部分节省下来的 kernel 启动开销。

**可断点 CUDA 图**通过允许在特定位置插入图断点同时解决这两个问题：计算被切分成多个捕获的图段，段与段之间用 eager（非图）执行衔接。这样既保留了 CUDA 图的大部分性能收益，又允许目标操作在图外运行。

<Note>
💡 AI Infra 学习笔记：CUDA 图的核心价值在于把大量 kernel 启动从「每步一次 CPU 调度」变成「一次录制、整体重放」，省掉每颗 kernel 约 5–10 µs 的启动开销——解码阶段 kernel 数量多、单颗又很短，这部分开销占比很高。但图的静态性（固定形状、固定地址）让它很难兼容动态控制流和调试；可断点 CUDA 图用「分段」在两者之间找平衡，是理解 CUDA 图能力边界的好案例。
</Note>

## 使用方法

### 调试模式：全部以 eager 方式运行

最简单的用途是调试。`--debug-cuda-graph` 参数把整个解码前向过程包在一个图断点里，于是每个操作都以 eager 方式运行，但仍走完整的 CUDA 图捕获/重放代码路径。这样你不用改模型代码就能调试 CUDA 图问题。

```bash
python -m sglang.launch_server \
    --model meta-llama/Llama-3.1-8B-Instruct \
    --debug-cuda-graph
```

该模式仅供调试——由于每个算子都以 eager 方式运行，它完全消除了 CUDA 图的性能收益。

### 在模型代码中做选择性图断点

生产环境使用中，你可以用 `@eager_on_graph` 装饰器把特定函数标记为「不可入图」。在 CUDA 图捕获期间，这些函数会在各捕获图段之间以 eager 方式运行；在捕获之外，它们表现如常。

```python
from sglang.srt.model_executor.runner_backend_utils.breakable_cuda_graph import eager_on_graph

@eager_on_graph(enable=True)
def my_dynamic_op(x):
    # This op is incompatible with CUDA graph capture
    return some_dynamic_operation(x)
```

你也可以用 `break_graph()` 辅助函数插入一个不带计算的裸图断点：

```python
from sglang.srt.model_executor.runner_backend_utils.breakable_cuda_graph import break_graph

def forward(self, x):
    x = self.layer1(x)
    break_graph()  # force a segment split here
    x = self.layer2(x)
    return x
```

要在环境层面启用可断点 CUDA 图（不用调试模式），设置环境变量：

```bash
export SGLANG_USE_BREAKABLE_CUDA_GRAPH=1
python -m sglang.launch_server \
    --model meta-llama/Llama-3.1-8B-Instruct
```

## 工作原理

### 捕获

可断点 CUDA 图扩展了 PyTorch 的 `torch.cuda.CUDAGraph`，把一次捕获拆分成被图断点分隔的多个段。

捕获期间的流程如下：

```
Begin capture (segment 1)
  ... graphable ops ...
  @eager_on_graph function encountered:
    1. End current capture segment
    2. Run the function eagerly (allocates output tensors)
    3. Record the function for later replay
    4. Begin new capture segment
  ... more graphable ops ...
End capture (segment N)
```

每个段都被独立实例化为一个可执行的 CUDA 图。非图函数及其参数引用会被保存下来，供重放时使用。

### 重放

重放期间：

```
For each segment i:
  1. Launch CUDA graph segment i
  2. Run the recorded non-graph function i eagerly
Launch final CUDA graph segment
```

非图函数会以捕获时相同的 tensor 引用被再次调用。由于这些引用指向 CUDA 图的静态输入/输出缓冲区，每次重放时它们都能看到更新后的值。

### 输出写回

当非图函数在重放期间产生输出时，结果必须写回下游图段所引用的同一批 tensor 缓冲区。该机制处理以下几种情况：

- **普通 tensor**：原地 `copy_()` 进原缓冲区。
- **结构化输出**（dataclass、带 tensor 属性的对象）：tensor 字段原地拷贝；非 tensor 字段直接替换。
- **tensor 字典**：tensor 值原地拷贝；非 tensor 值直接替换。

### 流的分叉/汇合跟踪

有些模型会把工作分叉到次要 CUDA 流上（例如用于计算重叠）。可断点 CUDA 图通过挂钩 `torch.cuda.Stream.wait_stream` 来跟踪哪些流从捕获流分叉出去。发生图断点时，所有分叉的流都会在结束当前捕获段之前被自动汇合回来，并在下一段开始后重新分叉。

<Note>
💡 AI Infra 学习笔记：分段图的难点在于「段间数据如何交接」：非图函数在 eager 下运行、产出新的 tensor，必须把结果写回下游图段引用的静态缓冲区（就地 copy），才能保证重放时数据连续。流的派生与汇合跟踪同理——图捕获期间派生出的流必须在段结束时汇合回捕获流，否则执行顺序无法保证。这些细节正是 CUDA 图工程化中「捕获失败」最常见的来源。
</Note>

## 兼容性

- **CUDA 与 ROCm/HIP。** 可断点 CUDA 图在 NVIDIA 和 AMD GPU 上都能运行。其他平台（NPU、CPU、MPS、XPU）不受支持；在这些平台上 `--debug-cuda-graph` 会被自动禁用并给出警告。
- **NVIDIA 上需要 `cuda-python`。** 流捕获状态查询通过 `cuda.bindings`（`pip install cuda-python`）使用 CUDA 运行时；可移植的 `torch.cuda.is_current_stream_capturing()` 在 CUDA 上已被证明不可靠。在 ROCm/HIP——`cuda-python` 不可用——则改用可移植的 `torch.cuda` API（其映射到 HIP 运行时）。
- **与内存节省模式不兼容。** 不能与 `SGLANG_MEMORY_SAVER_CUDA_GRAPH` 一起使用。

## 性能

当不插入任何图断点时，可断点 CUDA 图相比标准 CUDA 图的开销极小——捕获/重放路径几乎完全相同。

每个图断点会增加：
- 一次 `cudaGraphLaunch` 调用（重放断点前的图段）
- 一次 eager Python 函数调用
- 捕获期间一对 `cudaStreamBeginCapture` / `cudaStreamEndCapture` 调用

对于只有少量图断点的典型场景，相比捕获图段所节省的 kernel 启动开销，这部分开销可以忽略不计。
