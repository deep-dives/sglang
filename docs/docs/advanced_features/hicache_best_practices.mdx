## 为什么 HiCache 重要

SGLang HiCache 用三层分层 KV 缓存系统扩展了传统的 RadixAttention，大幅提升长上下文与多轮对话场景的性能。通过在 GPU 显存、主机内存与外部存储后端之间智能地管理 KV 缓存，HiCache 解决了限制传统系统缓存命中率的根本容量瓶颈。

<Note>
💡 AI Infra 学习笔记：缓存命中率（hit rate）是推理引擎最重要的性能指标之一——命中前缀缓存意味着跳过整段预填充计算，直接决定 TTFT 和吞吐量。HiCache 的核心思想是"显存不够，分层来凑"：把 KV 缓存按访问热度分层放置（GPU → CPU → 存储），热点留在最快的一层，冷数据下沉到容量更大的层次，从而在有限显存里最大化命中率。
</Note>

## 配置指南

## 核心 HiCache 参数

```bash Command
# Essential HiCache flags
--page-size 64                        # Page size for cache management
--enable-hierarchical-cache           # Enable HiCache
--hicache-ratio 2                     # Host memory ratio (2x GPU memory)
--hicache-size 100                    # Host memory size in GBs, will override the above ratio
--hicache-io-backend kernel           # The I/O backend of moving data between CPU and GPU
--hicache-write-policy write_through  # Cache write policy from GPU to CPU
--hicache-storage-backend             # Optional storage backend (e.g., hf3fs, mooncake, etc.)
```

注意事项：

- 除了在启动时配置 `--hicache-storage-backend`，SGLang 还支持通过 HTTP 管理端点对 HiCache 存储后端做**运行时挂载/卸载**（无需重启）。见 [HiCache 存储后端运行时挂载/卸载](./hicache_storage_runtime_attach_detach)。

## 启用存储后端时的关键配置

### 内存布局优化

```bash Command
# Page-first: Optimized for I/O efficiency with zero-copy (recommended with kernel backend)
--hicache-mem-layout page_first
# Page-first-direct: Optimized for direct I/O operations (Compatible with fa3 and same zero-copy performance as page_first)
--hicache-mem-layout page_first_direct
# Layer-first
--hicache-mem-layout layer_first
```
**布局兼容性：**
- `page_first`：只兼容 `kernel` I/O 后端，使用 `direct` 后端时会自动切换为 `layer_first`
- `page_first_direct`：专为 `direct` I/O 后端设计，内存组织方式经过优化

### 异构 TP 支持（GQA/MHA 模型）

当不同的部署使用不同的 TP 规模（例如 `tp=4` 与 `tp=8`）但共享同一个存储后端命名空间时，HiCache 存储支持跨集群的 KV 复用。

在 `--hicache-storage-backend-extra-config` 中使用 `tp_lcm_size`：

```bash Command
# Example: heterogeneous TP = {4, 8}, so lcm = 8
--hicache-storage-backend-extra-config '{"tp_lcm_size": 8}'
```

准则：

- 把 `tp_lcm_size` 设为所有共享同一 HiCache 存储的 TP 规模的最小公倍数（LCM）。
- 对于使用 Mooncake 和 `page_head` 布局的 MHA 模型，HiCache 会根据 `tp_lcm_size` 拆分头分片（head shard），使 key 能在异构 TP 部署之间复用。
- 如果所有集群使用相同的 TP 规模，则不需要该选项。

### 预取策略

```bash Command
# Best-effort: Terminate prefetch when needed
--hicache-storage-prefetch-policy best_effort
# Wait-complete: Ensure complete prefetch, higher cache reuse
--hicache-storage-prefetch-policy wait_complete
# Timeout: Balance between completion and best-effort
--hicache-storage-prefetch-policy timeout
```

<Note>
💡 AI Infra 学习笔记：把 KV 从存储拉回 GPU 需要时间，因此引擎会"预取"（prefetch）——在请求还没真正开始计算前，先异步把需要的 KV 搬上显存。`best_effort` 在有新请求要处理时随时中止预取，延迟低但命中率打折；`wait_complete` 保证搬完再算，命中率最高但可能拖慢首 token；`timeout` 是两者之间的折中。预取策略本质上是"等缓存 vs 赶时间"的取舍。
</Note>

### 与 PD 分离的集成

HiCache 与 PD 分离无缝配合。你可以在两种配置中选择：

1. **仅 Prefill 节点启用 HiCache**：只在 Prefill 节点上启用 HiCache，让 KV 缓存在各 Prefill 实例之间共享
2. **完整 HiCache + 异步卸载**：在 Prefill 节点上启用 HiCache，并在 Decode 节点上启用 KV 缓存异步卸载，让多轮对话场景中的 Prefill 节点能复用 Decode 节点的 KV 缓存

```bash Command
# Prefill node with HiCache enabled for cross-prefill sharing (ideal for SystemPrompt scenarios)
python3 -m sglang.launch_server \
  --model-path /xxx/DeepSeek-R1/ \
  --tp 8 \
  --host 0.0.0.0 \
  --port 10000 \
  --enable-metrics \
  --enable-cache-report \
  --mem-fraction-static 0.85 \
  --page-size 64 \
  --enable-hierarchical-cache \
  --hicache-ratio 2 \
  --hicache-size 0 \
  --hicache-mem-layout page_first_direct \
  --hicache-io-backend direct \
  --hicache-write-policy write_through \
  --hicache-storage-backend hf3fs \
  --hicache-storage-prefetch-policy wait_complete \
  --disaggregation-ib-device mlx5_0 \
  --disaggregation-mode prefill \
  --disaggregation-transfer-backend mooncake

# Decode node with async offloading enabled for KV cache reuse by Prefill (ideal for multi-turn conversations)
python3 -m sglang.launch_server \
  --model-path /xxx/DeepSeek-R1/ \
  --tp 8 \
  --host 0.0.0.0 \
  --port 10000 \
  --enable-metrics \
  --enable-cache-report \
  --page-size 64 \
  --hicache-ratio 2 \
  --hicache-size 0 \
  --hicache-mem-layout page_first_direct \
  --hicache-io-backend direct \
  --hicache-write-policy write_through \
  --hicache-storage-backend hf3fs \
  --hicache-storage-prefetch-policy wait_complete \
  --disaggregation-decode-enable-offload-kvcache \  # Enable async KV cache offloading in decode node
  --disaggregation-ib-device mlx5_0 \
  --disaggregation-mode decode \
  --disaggregation-transfer-backend mooncake
```

<Note>
💡 AI Infra 学习笔记：PD 分离把预填充和解码拆到不同节点，各自的显存压力完全不同——Prefill 节点大量产生 KV，Decode 节点则要长期持有 KV。把 HiCache 与 PD 分离结合：Prefill 节点写完 KV 就交给共享存储，多轮对话的下一轮可以从别的节点/存储直接复用，不必重新计算整段历史。这是超长上下文场景下"让 KV 在集群里流动起来"的关键架构。
</Note>

### 使用 Mooncake 部署 {#deployment-with-mooncake}

下面是用 Mooncake 部署 Qwen3-235B-A22B-Instruct-2507 的示例。更多细节见 [Mooncake 文档](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/storage/mooncake_store/README.md)。

```bash Command
# Set Mooncake environment variables
export MOONCAKE_TE_META_DATA_SERVER="http://127.0.0.1:8080/metadata"

python3 -m sglang.launch_server \
  --model-path $MODEL_PATH \
  --tp 8 \
  --page-size 64 \
  --enable-hierarchical-cache \
  --hicache-ratio 2 \

  --hicache-io-backend direct \
  --hicache-storage-backend mooncake \
  --hicache-write-policy write_through \
  --hicache-storage-prefetch-policy timeout
```


## 自定义存储后端集成

要接入一个新的存储后端：

1. **实现三个核心方法：**
   - `get(key)`：按键取值
   - `exists(key)`：检查键是否存在
   - `set(key, value)`：存储键值对

2. **注册你的后端：** 把存储后端注册到 HiCache 的 [BackendFactory](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/mem_cache/storage/backend_factory.py#L188)

HiCache 控制器会自动处理所有调度与同步。

### 动态加载后端

另外，你也可以用动态加载，避免把后端硬编码进仓库：

```bash Command
python3 -m sglang.launch_server \
  --model-path your-model \
  --enable-hierarchical-cache \
  --hicache-storage-backend dynamic \
  --hicache-storage-backend-extra-config '{"backend_name":"custom_backend_name", "module_path": "your_module_path", "class_name": "YourHiCacheClassName"}'
```

**配置参数：**
- `--hicache-storage-backend`：设为 `dynamic`
- `--hicache-storage-backend-extra-config`：JSON 配置，包含：
  - `backend_name`：自定义后端标识符
  - `module_path`：你的实现的 Python 模块路径
  - `class_name`：你的 HiCache 实现类名
  - `interface_v1`：0（禁用）或 1（启用），用于控制是否使用 batch_get_v1 与 batch_set_v1 方法
