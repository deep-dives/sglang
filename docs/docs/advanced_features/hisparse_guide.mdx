---

HiSparse 在解码阶段只在 GPU 上维护一个较小的"热点"（hot）KV 缓冲区，同时把完整的 KV 数据保存在 CPU 固定内存中，从而降低每个请求的 GPU 内存占用。再结合 PD 分离，可以显著提升解码并发度。

> **前置条件**：HiSparse 适用于使用 **DeepSeek 稀疏注意力（DSA）** 架构的模型（例如 DeepSeek-V3.2、GLM-5.1）以及 **DeepSeek V4**。这些模型天然只为部分 token 计算注意力，因此可以把 top-k 的 KV 保留在 GPU 上、把完整 KV 存在主机内存中，且不会损失精度。另外，HiSparse 目前**要求使用 PD 分离模式**，并且**只在 decode 实例上启用**。

<Note>
💡 AI Infra 学习笔记：稀疏注意力（Sparse Attention）的思想是"注意力不需要看所有 token"——某些架构（如 DeepSeek Sparse Attention）会让每个 token 只对一小部分相关 token 做注意力计算。HiSparse 正是利用了这一点：GPU 上只需放被选中的 top-k 热点 KV，完整 KV 全部沉到主机内存，于是单请求的显存占用从"整条序列"降为"固定大小的缓冲区"，解码并发度自然大幅提升。
</Note>

## 为什么需要 HiSparse？

在长上下文 LLM 推理中，每个解码请求都要在 GPU 上持有整条序列长度的 KV 缓存，这限制了 decode 实例能并发服务的请求数量。HiSparse 通过以下方式解决这个问题：

- **降低每个请求的 GPU 内存占用**：每个请求只占用一个固定大小的设备缓冲区（例如 4KB 个 token 槽位），而不是整条序列长度。
- **按需换入**：一个 CUDA kernel 根据注意力分数，动态地从主机内存加载最相关的 top-k 个 KV 条目。
- **对预填充透明**：HiSparse 完全是解码侧的优化，prefill 实例无需任何改动。

## 设计概览

### 解码工作流

每个解码步按以下流程进行：

1. **前向解码（Forward decode）** — 生成下一个 token
2. **Top-k 选择** — 通过注意力分数选出最相关的 token 位置
3. **换入（Swap-in）** — CUDA kernel 把 top-k 个 KV 条目从主机加载到设备缓冲区：
   - *短序列*（`seq_len ≤ device_buffer_size`）：快速路径，所有 KV 已在缓冲区中
   - *长序列*：命中检测 → LRU 重排 → 未命中处理（主机 → 设备拷贝）
4. **解码注意力（Decode attention）** — 用 top-k 个设备端位置计算注意力
5. **即时备份（Eager backup）** — 异步把上一个 token 的 KV 从设备拷贝到主机

### PD 分离集成（直写主机）

在 PD 分离模式下，prefill 实例通过 RDMA 把 KV 缓存直接写入 decode 实例的主机内存池，完全绕过 decode 侧的 GPU。这消除了 KV 传输过程中瞬时的 GPU 内存峰值，也去掉了暂存 DMA 这一步。

```
Prefill GPU  ──RDMA──▶  Decode Host Pool (CPU pinned memory)
                              │
                              ▼
                     alloc device buffer (4KB)
                              │
                              ▼
                     swap-in kernel (on-demand top-k)
```

对于 DeepSeek V4，直写主机路径只把 C4 KV 写入 decode 主机内存池，而 c4_indexer 与 C128 KV 仍然走设备到设备的传输。

<Note>
💡 AI Infra 学习笔记：这里的关键优化是"直写主机（direct-to-host）"——KV 传输路径从"GPU → GPU"变成"GPU → 主机内存池"，decode 侧连中间暂存都不需要，也就没有瞬时显存尖峰。把"放不下的 KV"从显存挪到主机/远端，本质上是把显存容量问题转成带宽问题，这也是 HiCache、HiSparse 等方案共同的设计哲学。
</Note>

## 部署

HiSparse 目前**要求使用 PD 分离模式**，并且**只在 decode 实例上启用**。

### Prefill 实例

```bash Command
python3 -m sglang.launch_server \
    --model-path /path/to/model \
    --trust-remote-code \
    --port 8000 --host 0.0.0.0 \
    --context-length 81920 \
    --chunked-prefill-size 65536 \
    --tp-size 8 --dp-size 8 --enable-dp-attention \
    --mem-fraction-static 0.85 \
    --disaggregation-mode prefill \
    --disaggregation-ib-device mlx5_0,mlx5_1,mlx5_2,mlx5_3 \
    --nnodes 1 --node-rank 0
```

### Decode 实例（启用 HiSparse）

```bash Command
python3 -m sglang.launch_server \
    --model-path /path/to/model \
    --trust-remote-code \
    --port 8000 --host 0.0.0.0 \
    --context-length 81920 \
    --tp-size 8 --dp-size 8 --enable-dp-attention \
    --mem-fraction-static 0.85 \
    --disable-radix-cache \
    --disaggregation-mode decode \
    --disaggregation-ib-device mlx5_0,mlx5_1,mlx5_2,mlx5_3 \
    --dist-init-addr 127.0.0.1:5757 \
    --nnodes 1 --node-rank 0 \
    --enable-hisparse \
    --hisparse-config='{"top_k": 2048, "device_buffer_size": 6144, "host_to_device_ratio": 10, "swap_in_block_size": 960}'
```

> **注意**：对于 DSA 模型，`--kv-cache-dtype` 默认为 `auto`，在 SM100+（Blackwell）上解析为 `fp8_e4m3`，在更老的架构上解析为 `bfloat16`。DSA 解码后端会根据 KV 数据类型自动选择（`bfloat16` → `flashmla_sparse`，`fp8_e4m3` → `flashmla_kv`）。DSA 后端参数只适用于 DSA 模型；DeepSeek V4 使用自己的 `dsv4` 注意力后端。


### 关键注意事项

- prefill 实例不需要 `--enable-hisparse`；它对 HiSparse 一无所知。
- 在 decode 实例上，启用 HiSparse 必须同时提供 `--enable-hisparse` 与 `--hisparse-config`。
- 对于 DSA 模型，`--kv-cache-dtype bfloat16` 使用 `flashmla_sparse`，`--kv-cache-dtype fp8_e4m3` 使用 `flashmla_kv`。
- 对于 DeepSeek V4，DSA 后端参数不适用。DeepSeek V4 默认使用 `dsv4` 注意力后端和 `fp8_e4m3` KV 缓存。
- `host_to_device_ratio` 应根据主机的可用内存来配置。例如：
  - **约 1 TB** 主机内存 → `host_to_device_ratio: 5`
  - **约 2 TB** 主机内存 → `host_to_device_ratio: 10`
