SGLang 支持在基础模型上使用 [LoRA 适配器](https://arxiv.org/abs/2106.09685)。借鉴 [S-LoRA](https://arxiv.org/pdf/2311.03285) 和 [Punica](https://arxiv.org/pdf/2310.18547) 的技术，SGLang 可以在同一个输入批次里高效支持多个 LoRA 适配器，让不同序列各自套用不同的适配器。

<Note>
💡 AI Infra 学习笔记：LoRA（低秩适配）是参数高效微调的主流方法——冻结基础模型权重，只训练很小的低秩矩阵（A×B，秩 r 通常 4~256），推理时把两个小矩阵的乘积加回原层输出。它的价值在于：一个基础模型可以同时挂成百上千个"专属技能"适配器（每个只有几十 MB），不用为每个下游任务存一份完整模型。多 LoRA 服务的难点是"同一批请求里的不同序列要用不同适配器"——这迫使 kernel 支持分段/分组的 GEMM（如 SGMV），否则不同适配器只能串行跑。S-LoRA 和 Punica 就是解决"多适配器 + 单批混合"的两个代表性方案，是推理引擎面试中"参数高效服务化"方向的高频考点。
</Note>

## LoRA 服务化相关参数


以下服务端参数与多 LoRA 服务相关：

* `enable_lora`：为模型启用 LoRA 支持。为了向后兼容，如果提供了 `--lora-paths`，该参数会自动设为 True。

* `enable_lora_overlap_loading`：启用异步 LoRA 权重加载，把 H2D 传输与 GPU 计算重叠起来。如果发现你的 LoRA 负载瓶颈在适配器权重加载上（例如频繁加载大 LoRA 适配器），应该开启它。

* `lora_paths`：要加载的 LoRA 适配器列表。每个适配器必须用以下格式之一指定：&lt;路径&gt; | &lt;名称&gt;=&lt;路径&gt; | 带 schema 的 JSON &#123;"lora_name":str,"lora_path":str,"pinned":bool&#125;。

* `max_loras_per_batch`：每个批次最多可用的适配器数量。这个参数会影响多 LoRA 服务预留的 GPU 显存量，显存紧张时应设小一些。默认是 8。

* `max_loaded_loras`：如果指定，会限制同一时刻 CPU 内存里最多加载多少个 LoRA 适配器。该值必须大于或等于 `max-loras-per-batch`。

* `lora_eviction_policy`：GPU 内存池满时的 LoRA 适配器驱逐策略。`lru`：最近最少使用（默认，缓存效率更好）。`fifo`：先进先出。

* `lora_backend`：运行 LoRA 模块 GEMM kernel 的后端。目前支持 Triton LoRA 后端（`triton`）和分块 SGMV 后端（`csgmv`）。未来会增加基于 Cutlass 或 Cuda kernel 的更快的后端。

* `max_lora_rank`：需要支持的最大 LoRA 秩。如果没指定，会从 `--lora-paths` 提供的适配器自动推断。如果你预期服务启动后要动态加载更大 LoRA 秩的适配器，就需要指定这个参数。

* `lora_target_modules`：应用 LoRA 的所有目标模块的并集（例如 `q_proj`、`k_proj`、`gate_proj`）。如果没指定，会从 `--lora-paths` 提供的适配器自动推断。如果你预期服务启动后要动态加载不同目标模块的适配器，就需要指定这个参数。也可以设为 `all` 来对所有支持的模块启用 LoRA。不过，在额外模块上启用 LoRA 会带来少量性能开销。如果你的应用对性能敏感，建议只指定你计划加载适配器的模块。

* `max_lora_chunk_size`：ChunkedSGMV LoRA 后端的最大分块大小。只在 `--lora-backend` 为 `csgmv` 时使用。取更大值可能提升性能。请根据你的硬件和工作负载调优。默认是 16。

* `lora_drain_wait_threshold`：当某个 LoRA 适配器的请求等待时间超过这个阈值（秒）时，调度器会有选择地腾出一个正在运行的适配器来腾出位置。这通过防止一小撮适配器霸占批次槽位，缓解高负载或不均衡负载下的极端尾延迟。设为 0 禁用该排空机制（默认）。

* `tp_size`：SGLang 支持 LoRA 服务与张量并行一起使用。`tp_size` 控制张量并行使用的 GPU 数量。张量分片策略的更多细节见 [S-LoRA](https://arxiv.org/pdf/2311.03285) 论文。

客户端这边，用户需要提供一个字符串列表作为输入批次，以及每个输入序列对应的适配器名称列表。


## 使用方法

### 服务单个适配器


**注意：** SGLang 通过两个 API 支持 LoRA 适配器：

1. **OpenAI 兼容 API**（`/v1/chat/completions`、`/v1/completions`）：使用 `model:adapter-name` 语法。示例见 [带 LoRA 的 OpenAI API](../basic_usage/openai_api_completions#using-lora-adapters)。

2. **原生 API**（`/generate`）：在请求体里传 `lora_path`（如下所示）。



```python Example
import json
import requests

from sglang.test.doc_patch import launch_server_cmd
from sglang.utils import wait_for_server, terminate_process
```


```python Example
server_process, port = launch_server_cmd(
    # Here we set max-loras-per-batch to 2: one slot for adaptor and another one for base model
    """
python3 -m sglang.launch_server --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --enable-lora \
    --lora-paths lora0=algoprog/fact-generation-llama-3.1-8b-instruct-lora \
    --max-loras-per-batch 2 \
    --log-level warning \
"""
)

wait_for_server(f"http://localhost:{port}")
```


```python Example
url = f"http://127.0.0.1:{port}"
json_data = {
    "text": [
        "List 3 countries and their capitals.",
        "List 3 countries and their capitals.",
    ],
    "sampling_params": {"max_new_tokens": 32, "temperature": 0},
    # The first input uses lora0, and the second input uses the base model
    "lora_path": ["lora0", None],
}
response = requests.post(
    url + "/generate",
    json=json_data,
)
print(f"Output 0: {response.json()[0]['text']}")
print(f"Output 1: {response.json()[1]['text']}")
```


```python Example
terminate_process(server_process)
```

### 动态 LoRA 加载


除了在服务启动时通过 `--lora-paths` 一次性指定所有适配器，你也可以通过 `/load_lora_adapter` 和 `/unload_lora_adapter` API 动态加载/卸载 LoRA 适配器。

使用动态 LoRA 加载时，建议在启动时显式指定 `--max-lora-rank` 和 `--lora-target-modules`。为了向后兼容，如果没显式提供，SGLang 会从 `--lora-paths` 推断这些值。但那样的话，你必须保证所有动态加载的适配器与初始 `--lora-paths` 里的适配器形状相同（秩和目标模块），或者严格"更小"。



```python Example
lora0 = "Nutanix/Meta-Llama-3.1-8B-Instruct_SFT_lora_4_alpha_16_humaneval_raw_json"  # rank - 4, target modules - q_proj, k_proj, v_proj, o_proj, gate_proj
lora1 = "algoprog/fact-generation-llama-3.1-8b-instruct-lora"  # rank - 64, target modules - q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj
lora0_new = "philschmid/code-llama-3-1-8b-text-to-sql-lora"  # rank - 256, target modules - q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj


# The `--target-lora-modules` param below is technically not needed, as the server will infer it from lora0 which already has all the target modules specified.
# We are adding it here just to demonstrate usage.
server_process, port = launch_server_cmd(
    """
    python3 -m sglang.launch_server --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --enable-lora \
    --cuda-graph-max-bs-decode 2 \
    --max-loras-per-batch 2 \
    --max-lora-rank 256
    --lora-target-modules all
    --log-level warning
    """
)

url = f"http://127.0.0.1:{port}"
wait_for_server(url)
```

### OpenAI 兼容 API 用法

你可以通过 OpenAI 兼容 API 使用 LoRA 适配器：在 `model` 字段中用 `base-model:adapter-name` 语法指定适配器（例如 `qwen/qwen2.5-0.5b-instruct:adapter_a`）。更多细节和示例见 OpenAI API 文档中的"Using LoRA Adapters"一节：[openai_api_completions](../basic_usage/openai_api_completions)。



### LoRA GPU 固定（Pinning）


另一个高级选项是在加载时把适配器指定为 `pinned`（固定）。固定后，适配器会永久分配到可用的 GPU 池槽位之一（由 `--max-loras-per-batch` 配置），运行期间不会被从 GPU 显存驱逐。它会一直驻留，直到显式卸载。

在同一个适配器被跨请求频繁使用的场景下，这可以避免重复的内存传输和重新初始化开销，从而提升性能。但 GPU 池槽位有限，固定适配器会降低系统按需动态加载其他适配器的灵活性。如果固定太多适配器，可能导致性能下降，最极端的情况（`固定适配器数量 == max-loras-per-batch`）会让所有未固定的请求停摆。因此，SGLang 目前把固定适配器的最大数量限制为 `max-loras-per-batch - 1`，以防止意外饥饿。

下面的例子中，我们启动一个服务，`lora1` 以固定方式加载，`lora2` 和 `lora3` 以普通（非固定）方式加载。请注意，我们故意用两种不同格式指定 `lora2` 和 `lora3`，以说明两种格式都支持。



```python Example
server_process, port = launch_server_cmd(
    """
    python3 -m sglang.launch_server --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --enable-lora \
    --cuda-graph-max-bs-decode 8 \
    --max-loras-per-batch 3 \
    --max-lora-rank 256 \
    --lora-target-modules all \
    --lora-paths \
        {"lora_name":"lora0","lora_path":"Nutanix/Meta-Llama-3.1-8B-Instruct_SFT_lora_4_alpha_16_humaneval_raw_json","pinned":true} \
        {"lora_name":"lora1","lora_path":"algoprog/fact-generation-llama-3.1-8b-instruct-lora"} \
        lora2=philschmid/code-llama-3-1-8b-text-to-sql-lora
    --log-level warning
    """
)


url = f"http://127.0.0.1:{port}"
wait_for_server(url)
```

## 选择 LoRA 后端

SGLang 支持两种 LoRA 后端，可以用 `--lora-backend` 参数选择：

- `triton`：基础的基于 Triton 的后端。
- `csgmv`：默认的分块 SGMV 后端，针对高并发场景优化。

`csgmv` 后端是最近引入的，用于尤其在高并发场景下提升性能。我们的基准测试显示，相比基础 triton 后端，它带来了 20% 到 80% 的延迟改善。



```python Example
server_process, port = launch_server_cmd(
    """
    python3 -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --enable-lora \
    --lora-backend csgmv \
    --max-loras-per-batch 16 \
    --lora-paths lora1=path/to/lora1 lora2=path/to/lora2
    """
)
```

## LoRA 重叠加载


使用 `--enable-lora-overlap-loading` 服务端参数，SGLang 引擎可以把 LoRA 权重的加载与 prefill 和 decode 计算重叠起来，本质上把 LoRA 权重的数据移动隐藏在 GPU 计算后面。我们的基准测试显示，在对抗性条件下，启用该特性可以让中位 TTFT 降低约 35%——详细基准见 [LoRA 重叠加载 PR](https://github.com/sgl-project/sglang/pull/15512)。



```python Example
lora0 = "Nutanix/Meta-Llama-3.1-8B-Instruct_SFT_lora_4_alpha_16_humaneval_raw_json"
lora1 = "algoprog/fact-generation-llama-3.1-8b-instruct-lora"
lora2 = "philschmid/code-llama-3-1-8b-text-to-sql-lora"


server_process, port = launch_server_cmd(
    """
    python3 -m sglang.launch_server \
    --model-path meta-llama/Meta-Llama-3.1-8B-Instruct \
    --enable-lora \
    --enable-lora-overlap-loading \
    --lora-paths lora0=Nutanix/Meta-Llama-3.1-8B-Instruct_SFT_lora_4_alpha_16_humaneval_raw_json \
    lora1=algoprog/fact-generation-llama-3.1-8b-instruct-lora \
    lora2=philschmid/code-llama-3-1-8b-text-to-sql-lora \
    --max-lora-rank 256 \
    --max-loras-per-batch 2 \
    --max-loaded-loras 4
    """
)

url = f"http://127.0.0.1:{port}"
wait_for_server(url)
```


```python Example
json_data = {
    "text": [
        "Write a very long fairy-tale.",
        "List 3 countries and their capitals.",
        "List 3 countries and their capitals.",
    ],
    "sampling_params": [
        {"max_new_tokens": 1024, "temperature": 0},
        {"max_new_tokens": 64, "temperature": 0},
        {"max_new_tokens": 64, "temperature": 0},
    ],
    "lora_path": ["lora0", "lora1", "lora2"],
}

# lora0 and lora1 will be loaded into the memory pool first, and because max_loras_per_batch = 2, lora2's request will remain in the queue.
# lora1's request will likely finish first, and once it does, lora2 will be loaded. With --enable-lora-overlap-loading, this loading will
# occur asynchronously and thus decoding for lora0's request won't be blocked.
response = requests.post(
    url + "/generate",
    json=json_data,
)

for i in range(3):
    print(f"Output from lora{i}: \n{response.json()[i]['text']}\n")
```

```python Example
terminate_process(server_process)
```

<Note>
💡 AI Infra 学习笔记：重叠加载的本质是"用计算掩盖数据搬运"——LoRA 适配器权重从 CPU 拷到 GPU（H2D）的延迟本来是阻塞的，异步加载让它在 prefill/decode kernel 跑的同时进行，用户感知不到等待。这背后的通用思想是"overlap 而非串行"：推理引擎里几乎所有性能优化（CUDA 图、多流、预取、流水线）都是让不同资源（磁盘、PCIe、SM）同时干活。但重叠不是免费的：需要固定（pinned）CPU 内存做异步拷贝，而且适配器到达 GPU 的时间错开，会削弱调度器把多个适配器拼进同一个 prefill 批的能力——所以它默认关闭，只在权重加载确实成为瓶颈时才开。理解这种"收益 vs 副作用"的权衡是系统设计的关键。
</Note>

#### LoRA 重叠加载的局限


不过，LoRA 重叠加载并非免费，有两个重要的注意事项：

1. **需要固定（pinned）CPU 内存**：
   异步 H2D 内存拷贝要求 LoRA 权重固定（pinned）在 CPU 内存中，而固定内存是有限的系统资源。为了控制固定内存的过度占用，SGLang 目前规定启用 LoRA 重叠加载时，`max_loaded_loras` 最多是 `max_loras_per_batch` 的 2 倍。

2. **多适配器 prefill 批处理能力下降**：
   启用重叠加载后，每个适配器是异步加载的，因此适配器在不同时间点才在 GPU 上就绪。这会削弱调度器组建多适配器 prefill 批次的能力——因为只有"适配器已加载"的请求才能被分到同一组。结果就是，不同适配器的请求会被调度到独立（或更小）的 prefill 批次里，当适配器加载时间相对 prefill 计算时间很小时，TTFT 反而会上升。这正是 LoRA 重叠加载默认关闭的原因：只有在确定 LoRA 权重加载是瓶颈时（例如适配器频繁换入换出、适配器权重很大、或 PCIe 受限的工作负载）才应该开启。



#### 重叠加载导致更高延迟的示例


例如，假设我们有四个 LoRA 适配器：`lora0`、`lora1`、`lora2` 和 `lora3`。加载任意一个适配器需要 2ms，而针对该适配器的请求的 prefill 步骤需要 20ms。

1. **基线**：
  引擎同步加载全部四个适配器，然后运行一个合并的 prefill 批次，总时间约为 `2 * 4 + 20 = 28ms`

2. **启用 LoRA 重叠加载**：
  引擎开始加载 `lora0`，一旦就绪就调度一个只含 `lora0` 的 prefill 批次，同时后台加载 `lora1`。然后调度 `lora1` 的 prefill，同时加载 `lora2`，依此类推。在 prefill 无法跨适配器批处理的最坏情况下，总时间约为 `2 + 4 * 20 = 82ms`

在这个场景里，重叠加载降低了适配器加载开销，但丢失多适配器 prefill 批处理带来的损失占主导，导致 TTFT 更高。
