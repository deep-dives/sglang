本文档是给把 SGLang 集成进 RL 与后训练系统的基础设施团队的实操指南。它聚焦循环里的运维痛点（rollout、评估、训练、权重同步），并把它们映射到具体的 SGLang API、参数和集成模式上。核心目标是在生产环境保持 rollout 服务行为一致的前提下，最大化 rollout 的效率、准确性和稳定性。

## 为什么在 RL 生命周期中用 SGLang？

让我们先接受一条来自早期 DeepMind RL 工程的指导原则：

**做一个库，而不是一个框架。**

这一理念通过把 SGLang 提供为灵活的工具而非僵化的结构来激发创新。以下是 RL 生命周期中使用 SGLang 的五个理由：

* **细粒度引擎睡眠与唤醒**：为最大功率的 rollout 和训练提供便利
* **开放易用的权重重装（Refit）功能**：支持共置或分离部署的多种方式
* **轻松推迟生成**：支持部分 rollout 和专门的 rollout 控制
* **确定性推理**：实现确定性推理，做到训练-推理零不一致
* **负载均衡路由器**：面向高吞吐 rollout 的缓存感知负载均衡

下面各节会详细展开这些方面。

<Note>
💡 AI Infra 学习笔记：强化学习（RL，尤其是 RLHF/GRPO）的训练循环是"采样（rollout）→ 奖励评估 → 策略更新 → 权重同步 → 再采样"的迭代过程。其中 rollout 阶段用当前策略模型大量生成样本，本质就是"用推理引擎跑高吞吐 LLM 推理"——这正是 SGLang 这类服务化引擎的用武之地。它和普通推理服务的差异在于：每轮训练后权重都要变、生成必须确定性一致（保证 on-policy 假设成立）、显存要在训练和 rollout 之间腾挪。理解"推理引擎在 RL 训练里扮演什么角色"，是 AI Infra 面试中"训练-推理协同"方向的核心问题。
</Note>

## 细粒度引擎睡眠与唤醒

Rollout 和训练都吃显存，把它们共置在同一批 GPU 上经常导致显存压力大、切换慢。SGLang 提供一种内存感知的睡眠/唤醒机制：释放 KV 缓存和权重，同时保持服务进程存活，之后无需完整重启即可为 rollout 恢复它们。这避免了每个 RL 步都重复磁盘 I/O 和 CUDA graph 重新捕获。

底层实现里，RL 团队通过 [torch_memory_saver](https://github.com/fzyzcjy/torch_memory_saver) 做支持 CUDA graph 的权重重定向（weight offload），以保留用于图回放（graph replay）的虚拟内存地址。详见：[Efficient RL Training - Optimizing Memory Usage in verl](https://hebiao064.github.io/rl-memory-management)。

<Note>
💡 AI Infra 学习笔记：睡眠/唤醒机制解决的是"训练与 rollout 抢显存"的问题。训练和 rollout 都希望独占 GPU 显存，最笨的做法是每次切换都杀进程重启服务——代价是重新读盘加载权重 + 重新做 CUDA graph 捕获，可能花好几分钟。SGLang 的做法是"软释放"：用 torch_memory_saver 把权重和 KV 缓存的显存归还给训练，但保留进程和虚拟内存地址，训练完再把权重重新放回同一地址，CUDA graph 因为地址没变可以直接重放、不用重新捕获。这个"保住虚拟地址 = 保住 CUDA graph"的技巧是训练-推理共置的核心工程细节。
</Note>

## 开放易用的权重重装（Refit）功能

每步训练结束后，rollout 引擎必须装上新的权重。SGLang 支持三种重装策略，让你能匹配自己的基础设施风格（共置 vs 分离部署）和扩展需求。每种策略都对应一个具体的 API 和清晰的请求 schema。想深入了解 SGLang 的权重更新工具，见 [RL System Deep Thinking: Weight Update Mechanisms](https://github.com/zhaochenyang20/Awesome-ML-SYS-Tutorial/blob/main/rlhf/sys-design/readme-1-EN.md)。

**如何选择：**

- **从磁盘加载**最简单，最适合弹性 rollout 扩缩容和检查点。
- **从张量加载**最适合共置训练/rollout，可以直接传内存中的张量。
- **从分布式加载**最适合分离部署的训练/rollout，使用专门的通信组（NCCL/IB）。

### 从磁盘更新权重

**适用场景：**

- 把检查点保存到磁盘，再从磁盘更新权重
- 动态扩缩容（新的 rollout 实例可以从同一个检查点加载）

**为什么它效果好：**

这条路用一点 I/O 开销换取简单和灵活。它与检查点机制自然集成，而且让新增 rollout 引擎变得微不足道：指向同一个检查点、调用 API 即可。它对高可用也是最安全的选择，因为检查点本身就是事实来源。

**Python 引擎 API：** `engine.update_weights_from_disk(model_path, load_format=None)`

**扩散引擎（SGLang-Diffusion）：** 扩散引擎暴露了同样的 `POST /update_weights_from_disk` 端点，行为如下：

- **全有或全无 + 回滚：** 如果任何模块加载失败，所有此前更新过的模块都会通过重新加载原始模型路径回滚到原始权重。不会留下部分更新。如果回滚本身也失败，异常会向上传播，让调用方知道模型已处于不一致状态。
- **卸载感知：** 启用逐层卸载（`--dit-layerwise-offload`）时，扩散卸载管理器会把 GPU 参数替换成小的 `torch.empty((1,))` 占位符，而真实权重存放在合并的固定（pinned）CPU 缓冲区里。朴素的 `param.data.copy_()` 会因形状不匹配而失败。因此更新器会动态检测活跃的卸载管理器，直接把新权重写进它们的 CPU 缓冲区，完全绕过占位符。如果某个层在更新时恰好被预取到 GPU 上，对应的 GPU 实时张量也会被更新，让改动立即生效。这不需要额外 GPU 显存，也不会打扰卸载状态。
- **DTensor 感知：** 通过 `torch.distributed.tensor`（张量并行）分布的参数会通过 `distribute_tensor` 更新，保证每个分片被正确放到对应的设备网格上。

## 轻松推迟生成

多轮 RL rollout 经常被长尾请求拖累，阻塞整个批次。少量慢交互就能拖住所有 GPU，而且长尾行为让性能剖析和监控都变得困难。

SGLang 暴露了明确的暂停/恢复 API，让你可以暂停慢请求、稍后继续。这个模式与 [APRIL](https://arxiv.org/abs/2509.18521) 等系统一致：收集到足够的响应就终止，把未完成的响应留到下一步复用。结果是在不丢弃部分工作的前提下提高 GPU 利用率。

从训练更新权重时，`pause_generation` --- 更新权重 --- `continue_generation` 是正确的执行流程。只有 SGLang 没有在积极处理推理任务时才能做权重更新。

**模式：**

- `abort`：默认行为，等同于带 `abort_all` 设置的 `abort` 端点。`waiting_queue` 和 `running_queue` 里待处理的请求会立刻返回给调用方。
- `retract`：让引擎进入"已暂停"状态。把运行中的请求移回等待队列。KV 缓存可以稍后冲刷并重新计算。
- `in_place`：让引擎进入"已暂停"状态，但不改变请求的状态。运行中的请求依赖 KV 缓存的可用性才能继续，所以任何后续的 `flush_cache` 调用都会失败。

## 确定性推理

在许多 RL 技术栈里，rollout 和训练用不同的 kernel 或批处理行为实现。即使权重完全相同，token 概率也可能漂移，悄无声息地破坏 on-policy 假设。这就是训练-推理不一致问题。

SGLang 支持一种确定性推理模式，减少跨批形状的非确定性。这缓解了运行时批处理和 kernel 选择引入的方差。要进一步实现真正的 on-policy 训练，需要把训练引擎也改成使用相同的确定性 kernel。实现细节见这些 miles 示例：[True On-Policy](https://github.com/radixark/miles/tree/main/examples/true_on_policy) 和 [True On-Policy for VLM](https://github.com/radixark/miles/tree/main/examples/true_on_policy_vlm)。更多背景见博客 [Let Speed Be With Stability: All-In-One Solution to Training-Inference Mismatch with Miles](https://github.com/zhaochenyang20/Awesome-ML-SYS-Tutorial/blob/main/rlhf/slime/mismatch/blog-en.md)。

<Note>
💡 AI Infra 学习笔记：训练-推理不一致（training-inference mismatch）是 RL 训练里一个隐蔽但致命的坑：RL 的 on-policy 假设是"我们优化的策略就是用来采样的策略"，如果 rollout 引擎和训练引擎的 kernel 不同、批形状不同，同一个权重算出的 token 概率会略有差异，导致收集到的样本和理论分布对不上，训练就会悄悄变坏。根源是浮点累加顺序、kernel 选择等带来的非确定性。SGLang 的确定性推理模式通过固定 kernel 和批处理行为来减小这类漂移；要做到完全一致，还要训练引擎也用同一套确定性 kernel。这是"推理引擎 × RL 训练协同"里最硬核的知识点之一。
</Note>

**服务端参数：**

```text Output
--enable-deterministic-inference
```

更多细节见 [确定性推理](./deterministic_inference)

## 负载均衡路由器

SGLang Model Gateway 是大型 RL rollout 推荐的控制面。它提供异步、非阻塞的请求处理、缓存感知的负载均衡，以及在 rollout 和奖励服务器之间的容错路由。这让你能保持 GPU 满载，同时避免长尾停顿和脆弱的引擎本地并发逻辑。它已被用于 GLM 4.5+ 模型的训练，并被证明在生产级大规模 RL 负载下非常高效。

对 RL 基础设施的关键收益：

- **异步非阻塞效率**：SGLang 原生的异步服务/路由架构（HTTPS/gRPC）自动管理并发。这保证了最大的 GPU 饱和度和有效的连续批处理，无需工程师做复杂的自研实现。
- **弹性与容错**：把奖励模型和 rollout 封装成独立服务器，SGLang 在逻辑和物理上都把它们解耦。这种架构为大规模分布式训练提供了健壮的灾难恢复：如果某个服务器失败，路由器会自动把流量重定向到健康节点，保证训练过程不中断。
- **训练-推理对齐**：训练和推理都使用 SGLang Model Gateway，保证"所见即所得"。这消除了分数差异，以及训练与部署使用不同引擎时常见的痛苦的后端对齐问题。
- **动态负载均衡与长尾缓解**：与静态分区不同，SGLang Model Gateway 支持多轮 RL 的请求级动态调度。它可以把一段对话的不同轮次分发到不同服务器，平衡负载并消除序列长度不同带来的长尾延迟。

部署和配置见：[SGLang Model Gateway](./sgl_model_gateway)
