## 1. 模型介绍

**GLM-5.2** 是智谱 AI 的旗舰混合专家模型，基于 **DeepSeek 稀疏注意力（DSA）** 构建：一个极快的 indexer 为每个 query 选出少量关键 token（top-2048），使注意力成本在上下文变长时几乎保持恒定。它提供两种精度——**FP8**（`zai-org/GLM-5.2-FP8`）和全精度 **BF16**（`zai-org/GLM-5.2`）——两者都具备 **78 层 transformer**、**256 个路由专家**（每个 token 激活 8 个）、**1M token 上下文窗口**，以及一个 **MTP（多 token 预测）** 层用于内置的 EAGLE 式投机解码。FP8 是推荐的部署方式；BF16（约 1.5 TB）需要 8×B300 节点或多节点环境。在 Blackwell 上，NVIDIA 还发布了 **NVFP4** 版本（`nvidia/GLM-5.2-NVFP4`），只把 MoE 专家的线性层权重和激活量化为 4 位（共享专家保持不量化），在 GPQA Diamond、SciCode 和 IFBench 上精度与 FP8 基线相差约 1 个百分点以内。

## 2. 配置技巧

- **DeepSeek 稀疏注意力（DSA）。** GLM-5.2 使用 `glm_moe_dsa` 架构；SGLang 会自动选择 DSA 注意力后端（prefill 用 `flashmla_sparse`、decode 用 `fa3`、indexer topk 用 `sgl-kernel`）。在支持的硬件上无需指定 attention-backend 参数。SGLang 也会自动为 DSA 模型选择 KV 缓存精度——Blackwell（B200/GB300/B300，此时 DSA 走 TensorRT-LLM 后端）用 `fp8_e4m3`，Hopper（H200）用 `bf16`——所以无需 `--kv-cache-dtype` 参数。在 Hopper 上，把 `--kv-cache-dtype fp8_e4m3` 与 `--dsa-prefill-backend flashmla_sparse_q8 --dsa-decode-backend flashmla_kv` 组合使用，可启用原生的 FP8 稀疏 prefill kernel（直接在 fp8 KV 缓存上计算，无需 fp8→bf16 反量化往返；GLM-5.2 的 64 个 query 头与该 kernel 的原生 tile 匹配）——kernel 细节请参考 [DeepSeek-V3.2 页面](../DeepSeek/DeepSeek-V3_2)；可选的 `SGLANG_ENABLE_DSA_Q8KV8_*` 性能环境变量在 `python/sglang/srt/environ.py` 中有文档说明。
- **MTP / 投机解码。** 检查点内置一个 nextn 层。启用 EAGLE MTP 可降低延迟（低延迟用 `--speculative-algorithm EAGLE --speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6`；均衡用 `1-1-2`）。配置里的 `index_share_for_mtp_iteration` 会在草稿步骤之间复用 DSA indexer 的 topk（仅在 `--speculative-eagle-topk 1` 时有效）。**草稿长度要对齐接受长度。** GLM-5.2 的 MTP 头很强——接受长度通常很高（许多负载下 4+，低延迟运行中接近饱和的 5–6）。请留意服务端报告的**接受长度**，并据此调整 `--speculative-num-steps` / `--speculative-num-draft-tokens`：当接受长度还接近草稿 token 数时，还有余量可以继续调高（每一步接受更多 token）；如果它明显偏低，就调低——每个被拒绝的草稿 token 都是白费的验证计算。

<Note>
💡 AI Infra 学习笔记：MTP（Multi-Token Prediction，多 token 预测）是投机解码的一种实现——模型额外训练一个「nextn」头，一次预测接下来多个 token 作为草稿，再由主模型并行验证。它不需要单独的草稿模型，而是复用主模型的表示，因此是 EAGLE 式方法里省显存又提速度的代表。调优关键看「接受长度」（accept length）：它接近草稿数说明草稿质量高、还有提升空间；一旦远低于草稿数，再多预测也只是浪费验证算力。
</Note>

- **显存。** FP8 权重很大（是 MoE 全部参数，而非激活参数）。H200（TP8）上可从 `--mem-fraction-static 0.8` 起步再往上调；4 卡 GB300 单节点布局（TP4）则调高它。
- **DP-Attention + DeepEP** 用于均衡/高吞吐策略：把注意力分散到数据并行 rank 上，并让 MoE 走 DeepEP 路由。
- **BF16 权重需要更多 GPU。** 全精度版本（`zai-org/GLM-5.2`，约 1.5 TB）无法装进单个 8×H200 / 8×B200 / 4×GB300 节点。它可以在 **8×B300**（TP8，约 2.1 TB HBM）上单节点运行——**已验证**；在更小的 GPU 上需要 **多节点** 布局（例如 2×8×H200 或 2×8×B200 用 TP16、2×4×GB300 用 TP8），而这些 **多节点 BF16 方案仍属于建议/推断**（`verified: false`）。FP8 是推荐的部署方式。DSA / MTP / chunked-prefill 的用法与 FP8 相同。在 B300 上，BF16 低延迟与 FP8 持平（sm103 的 FP8 路径尚未优化），但在均衡/高吞吐点上 FP8 更优。
- **PD 分离（prefill/decode）。** GLM-5.2 是 DSA 模型，可在 prefill/decode 分离部署下运行——在[上方 Playground](#playground) 中切换 **PD Disagg** 卡片（选择 Prefill/Decode 角色 + 传输后端，再用 `sglang_router.launch_router --pd-disaggregation` 作为前端）。Mooncake 后端**会自动检测 InfiniBand HCA**，默认无需指定设备参数；只有当自动检测选错设备或 KV 传输连不上时，才需要添加 `--disaggregation-ib-device mlx5_0`（你的网卡）。在 H200 Docker 里要先把 IB HCA 暴露给容器（`--privileged --ulimit memlock=-1`，或 `--device /dev/infiniband:/dev/infiniband --cap-add IPC_LOCK`）——不暴露 IB，Mooncake 会悄悄回退到 TCP。
- **chunked-prefill 大小与场景相关。** 长输入（8K+）下，默认的 `--chunked-prefill-size 2048` 太小，会让均衡点受限于 prefill（排队主导 TTFT）。在均衡方案上把 `--chunked-prefill-size 32768` 后，我们在 8×H200 和 8×B200（8K 入 / 1K 出）上测到输出吞吐**提升约 +34–78%、TTFT 下降约 −39–59%**。对高吞吐**没有影响**（那里是 decode 受限）——保持默认即可。`--max-running-requests` 反映的是 KV 容量，不是可以随便调大的参数：单个 8 卡节点大约能装下 60–90 个并发 8K+1K FP8 请求，所以均衡方案建议固定到 `--max-running-requests 80` 附近，高吞吐则放开跑。

- **AMD GPU（MI300X / MI325X / MI355X）。** FP8（`zai-org/GLM-5.2-FP8`）在这三款上都能以 `tp=8` 单节点运行。BF16（`zai-org/GLM-5.2`，约 1.51 TB）只有 **MI325X**（2 TB HBM）和 **MI355X**（2.3 TB）能单节点装下；**MI300X**（1.5 TB）单节点放不下 BF16 权重加 KV 缓存，所以那里请用 FP8（或等验证通过后采用多节点 BF16 布局）。使用 DSA tilelang 后端（`--dsa-prefill-backend tilelang --dsa-decode-backend tilelang`），并添加 `--chunked-prefill-size 131072` 和 `--watchdog-timeout 1200`（为权重加载预留 20 分钟）。FP8 大约只用 BF16 一半的显存（约 89 GB/卡 vs 约 175 GB/卡）。GLM-5.2 与 DeepSeek-V3.2 共享相同的模型结构；其它 DSA / HiSparse 技巧请参考 [DeepSeek-V3.2 cookbook](../DeepSeek/DeepSeek-V3_2)。

<Note>
**gfx950 块级 FP8 精度问题：已在固定的 MI355X 镜像（`v0.5.13.post1-rocm720-mi35x-20260618`）中修复。** 更早的 SGLang ROCm 镜像在 gfx950（ROCm 7.2）上错误编译了 AMD aiter 的 `gemm_a8w8_blockscale_bpreshuffle` GEMM：单层误差很小，但会跨全部 78 层累积并静默破坏输出——上下文推理失效（GSM8K ≈ 0），而短的简单事实性提示看起来却正常。根因是 gfx950/ROCm 7.2 对 CK kernel 的错误编译（一个依赖 LLVM 类型转换 pass 的打包非法类型 FMA，而该 pass 在 ROCm 7.2 中被移除；tile 边界附近会出现不确定的错误行）。该问题已在固定镜像及更新版本中解决：GLM-5.2-FP8 在 MI350X/MI355X（gfx950）上已按 TP4 和 TP8 重新验证——**GSM8K ≈ 0.96（0% 无效）**，**15/15 针尖检索到约 118K token**。**MI300X / MI325X（gfx942）从未受影响。** 如果必须使用旧镜像，请把 gfx950 的 FP8 输出视为未验证。背景：[sgl-project/sglang#28685](https://github.com/sgl-project/sglang/issues/28685)（分析）以及上游 CK 修复 [ROCm/rocm-libraries#8639](https://github.com/ROCm/rocm-libraries/pull/8639)（标量 FMA + 累加器锚定；在 -O3 下恢复正确性与确定性）。
</Note>

- 在 Deploy 面板中，AMD 的 **MTP / EAGLE 投机解码**被禁用。此前导致其退化的块级 FP8 精度 bug 现已修复（见上方说明），但 gfx950 上的 MTP 仍依赖投机解码草稿 kernel，而该 kernel 尚未在此硬件上验证（且 `--speculative-num-steps > 3` 时还会遇到另一个构建问题）。在 MTP 于 gfx950 上验证通过之前，请省略 `--speculative-*` 参数，不带 MTP 提供服务。

## 3. 高级用法

### 3.1 推理

GLM-5.2 是混合推理模型。启用 `glm45` 推理解析器（在[上方 Playground](#playground) 的 **Parsers** 卡片中切换 **Reasoning Parser**），即可把思考与最终答案分开——思考落在 `message.reasoning_content`，答案在 `message.content`。思考默认开启；用 `chat_template_kwargs: {"enable_thinking": False}` 关闭（模板变量名是 `enable_thinking`，不是 `thinking`）。

**推理强度。** 传入 `chat_template_kwargs: {"reasoning_effort": ...}` 可注入一行 `Reasoning Effort: <level>` 系统提示（仅在思考开启时生效）。**模板只接两个有效级别——`Max` 和 `High`——如果你完全不传 `reasoning_effort`，得到的就是 `Max`，即最高档。** `"high"` 是**唯一**会降低强度的值；其它任何值（包括 `"low"` 和 `"medium"`）都会回退到 `Max`：

| `reasoning_effort` | 注入的系统行 | 效果 |
|---|---|---|
| *（未传入 / 未设置）* | `Reasoning Effort: Max` | **默认——最高强度推理** |
| `"high"` | `Reasoning Effort: High` | 把推理强度**调低** |
| `"low"`、`"medium"` 或任何其它值 | `Reasoning Effort: Max` | 回退到 `Max`（不是独立级别） |

<Accordion title="推理示例（Python）">

```python Example
from openai import OpenAI

client = OpenAI(base_url="http://localhost:30000/v1", api_key="EMPTY")
resp = client.chat.completions.create(
    model="zai-org/GLM-5.2-FP8",
    messages=[{"role": "user", "content": "What is 15% of 240?"}],
    extra_body={"chat_template_kwargs": {"enable_thinking": True, "reasoning_effort": "high"}},
)
msg = resp.choices[0].message
print("Reasoning:", getattr(msg, "reasoning_content", None))
print("Answer:", msg.content)
```

</Accordion>

<Accordion title="输出示例">

```text Output

2.  **Convert the percentage to a decimal:** 15% = 0.15
3.  **Multiply by the total:** 0.15 * 240 = 36
    (Quick mental math: 10% of 240 = 24; 5% = 12; 24 + 12 = 36.)

Answer: 15% of 240 is **36**.

Here is how you can calculate it:
0.15 × 240 = 36
```

### 3.2 工具调用

启用 `glm47` 工具调用解析器（在[上方 Playground](#playground) 的 **Parsers** 卡片中切换 **Tool Call Parser**），即可通过 `message.tool_calls` 暴露结构化工具调用。GLM-5.2 输出的是较新的 `<tool_call>…<arg_key>…<arg_value>…` 格式，所以需要 **`glm47`** 解析器——较旧的 `glm45` 解析器解析不了它（调用会作为原始文本留在 `content` 里）。思考模式下，这一轮也会填上 `reasoning_content`，所以两个字段都要打印。

<Accordion title="工具调用示例（Python）">

```python Example
from openai import OpenAI

client = OpenAI(base_url="http://localhost:30000/v1", api_key="EMPTY")
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get the current weather for a city",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"],
        },
    },
}]
resp = client.chat.completions.create(
    model="zai-org/GLM-5.2-FP8",
    messages=[{"role": "user", "content": "What's the weather in Paris?"}],
    tools=tools,
)
msg = resp.choices[0].message
print("Reasoning:", getattr(msg, "reasoning_content", None))
print("Tool calls:", msg.tool_calls)
```

</Accordion>

<Accordion title="输出示例">

```text Output
Reasoning: The user wants to know the weather in Paris. I'll call the get_weather function with "Paris" as the city.

Tool calls: [
  {
    "id": "call_13fcd52146934b7781d06d4a",
    "type": "function",
    "function": {"name": "get_weather", "arguments": "{\"city\": \"Paris\"}"}
  }
]
```

</Accordion>

### 3.3 HiCache（分层 KV 缓存）

对长上下文、前缀密集的负载，可启用分层 KV 缓存，把冷 KV 块溢出到主机内存（在[上方 Playground](#playground) 中切换 **Hierarchical KV Cache** 卡片）。考虑到 GLM-5.2 的 1M token 窗口，这一特性很有用；把 `--hicache-ratio` 与符合你复用模式的写入策略搭配使用。

<Note>
💡 AI Infra 学习笔记：分层 KV 缓存（HiCache）解决的是「1M 上下文下 KV 缓存撑爆显存」的问题——把访问频率低的冷 KV 块按层级移到主机内存，热 KV 块留在显存，用少量访问开销换显存容量。它和前缀缓存（RadixCache）、KV 量化是长上下文场景降低显存压力的三条主要手段，经常组合使用。
</Note>

### 3.4 Claude Code 集成

GLM-5.2 强大的推理 + 工具调用能力，使它很适合做 [Claude Code](https://code.claude.com/docs/en/overview)（Anthropic 的 Agent 化 CLI）的后端。SGLang 在每台服务器上都暴露了兼容 Anthropic 的 `/v1/messages` 端点，所以 Claude Code 只需设置环境变量就能对接 GLM-5.2 服务器——无需改代码。用 `--reasoning-parser glm45 --tool-call-parser glm47` 启动服务器（上面 Deploy 面板的任意方案都可以），然后：

```bash Command
export ANTHROPIC_BASE_URL="http://127.0.0.1:30000"
export ANTHROPIC_AUTH_TOKEN="dummy"
export API_TIMEOUT_MS="3000000"
export CLAUDE_CODE_AUTO_COMPACT_WINDOW="1000000"
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
export CLAUDE_CODE_ATTRIBUTION_HEADER=0
export ANTHROPIC_DEFAULT_HAIKU_MODEL="glm-5.2[1m]"
export ANTHROPIC_DEFAULT_SONNET_MODEL="glm-5.2[1m]"
export ANTHROPIC_DEFAULT_OPUS_MODEL="glm-5.2[1m]"
claude
```

其中两项对 GLM-5.2 尤其重要：

- **`CLAUDE_CODE_ATTRIBUTION_HEADER=0`**——Claude Code 会在系统提示词前附加一段按请求生成的 attribution 块。GLM-5.2 的对话模板把 `tools` 渲染在 `system` **之前**，于是每轮之间最先变化的就是这个按请求生成的哈希，导致 Radix 前缀缓存每轮都要重新 prefill 整个系统提示词加历史。这个环境变量会去掉该块，恢复前缀缓存复用。
- **用 `glm-5.2[1m]` 作为模型名**——`[1m]` 后缀是客户端侧的提示，用于启用 Claude Code 的 1M 上下文测试版，正好匹配 GLM-5.2 的 1,048,576 token 窗口。不加它，上下文会被限制在远低于 1M 的水平。SGLang 不校验 `model` 字段，所以服务端接受任何名字。

完整配置（流式、工具使用、count_tokens、在 `~/.claude/settings.json` 持久化环境变量、故障排查）请参考 [Anthropic 兼容 API](../../../docs/basic_usage/anthropic_api)。

### 3.5 上下文并行

长上下文下的 prefill 上下文并行有助于降低 TTFT。要为 GLM 5.2 启用 prefill 上下文并行，请追加以下参数：
```bash
--attn-cp-size 8 \
--enable-prefill-cp \
--cp-strategy interleave \
```
它会在注意力前向阶段把序列等分到 `--attn-cp-size` 个 rank 上。prefill CP 的代价是会在 indexer-topk 和注意力 kernel 之前引入额外的 all-gather 操作，因此会提高 decode（统一部署下）或短 prefill 的延迟。

使用 PD 分离部署时，prefill 节点可以选择启用 [LayerSplit](https://z.ai/blog/scaling-pain) 技术：
```bash
--enable-dsa-cache-layer-split \
--attn-cp-size 8 \
--cp-strategy interleave \
```
启用 LayerSplit 后，每个 rank 上的 KV 缓存可以按 CP 注意力组做分片，并在需要时预取。这最多能把 KV 缓存显存降低 75%，从而提升 prefill 侧的吞吐量。
