Instruct 检查点以 **FP4 MoE 专家 + FP8 注意力/稠密层**的形式发布（一个混合精度检查点即可覆盖所有支持 FP4 的 GPU）。对应的 `*-Base` 仓库发布纯 FP8 混合检查点，仅供继续预训练使用——不用于聊天或工具调用。

**亮点：** 混合 CSA + HCA 注意力（在 1M 上下文下相比 DSv3.2 推理 FLOPs 约 -27% / KV 缓存约 -10%）、流形约束超连接（mHC）、Muon 优化器、**1M token 上下文**（32T+ 预训练 token）、三种推理模式（*Non-think* / *Think High* / *Think Max* —— Think Max 需 ≥ 384K 上下文），以及专用的 `encoding_dsv4.encode_messages` Python 编码器 + DSML 工具调用文法。

**推荐的生成参数：** `temperature=1.0`，`top_p=1.0`。

**资源：** HuggingFace · [Flash Official (0731)](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash-0731) · [Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash) · [Pro](https://huggingface.co/deepseek-ai/DeepSeek-V4-Pro) · ModelScope · [Flash](https://modelscope.cn/models/deepseek-ai/DeepSeek-V4-Flash) · [Pro](https://modelscope.cn/models/deepseek-ai/DeepSeek-V4-Pro)。

<Note>
💡 AI Infra 学习笔记：DeepSeek-V4 的混合注意力（CSA + HCA）是稀疏/压缩注意力的进一步演进——把大部分注意力压缩成紧凑状态，显著降低推理 FLOPs 与 KV 缓存；1M 上下文下相比 DSv3.2 的 FLOPs 与 KV 缓存都有约一个数量级的下降幅度。再叠加 MegaMoE（把专家分派与 GEMM 融合进单个 kernel）与 DSpark（内置草稿头投机解码），长上下文与解码吞吐两大瓶颈被一起优化。这类"压缩注意力 + 融合 MoE"组合是下一代推理引擎优化的主要方向。
</Note>

## 2. 配置技巧

{/* TODO: expand this section as more recipes are validated end-to-end. */}

**并发与 DeepEP 分派缓冲**

必须满足：`max-running-requests × MTP_draft_tokens ≤ SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK`。违反它会在稳态负载下撑爆 DeepEP 的分派缓冲（`deep_ep.cpp:1105`）。调优时，把 `--cuda-graph-max-bs-decode`、`--max-running-requests` 与环境变量一起调整。

命令生成器目前取值偏**保守**（镜像自内部压测矩阵）。它们开箱即用、安全运行，但很可能留了吞吐量余量——请按你实际负载的峰值并发向上调优，并把结果反馈回来，以便修订默认值。

**投机解码**

原始 Flash 与 Pro 方案使用 EAGLE。Flash Official (0731) 使用内置的 DSpark 草稿头；启动与调优说明见 [DSpark](#3-4-dspark-speculative-decoding)。

对于原始 Flash 与 Pro 检查点：

- `low-latency`：steps=3、draft-tokens=4 → 在 bs=1 时收益最大。
- `balanced`：steps=1、draft-tokens=2 → 更温和的 MTP，减少高批大小下的吞吐损失。
- `high-throughput`：禁用 MTP —— 饱和时验证步骤的成本超过了收益。
- MTP 运行在 v2 投机路径上。

**压缩注意力状态 dtype**

DeepSeek-V4 使用混合压缩注意力来提升长上下文效率。`SGLANG_DSV4_COMPRESS_STATE_DTYPE` 控制 C4 / C128 压缩注意力状态池的 dtype。支持 `float32` / `fp32`（默认：`float32`）与 `bfloat16` / `bf16`。要在离线压缩路径上使用 BF16：

```bash Command
SGLANG_DSV4_COMPRESS_STATE_DTYPE=bf16 \
sglang serve \
  --model-path deepseek-ai/DeepSeek-V4-Flash \
  <other args>
```

该 BF16 设置只作用于压缩注意力状态池，减少每个压缩状态槽位的 GPU 显存占用。它不改变模型权重精度或主 KV 缓存的 dtype。在自动池大小、无显式容量上限的情况下，同样的显存预算可以容纳更多槽位，启动日志会显示更大的 `c4_state` 与 `c128_state` 池大小。保守起见请保持默认的 `float32`。

**EPLB + Waterfill（实验性）**

要复现记录的/静态 EPLB，先按 [在 MoE 模型中捕获专家选择分布](../../../docs/basic_usage/native_api.mdx#capture-expert-selection-distribution-in-moe-models) 记录一份专家分布文件。复现运行用生成的 `expert_distribution_recorder_*.pt` 作为初始专家位置。**该特性请切换到最新 main 分支。**

非 PD 复现使用：

```bash Command
--moe-a2a-backend deepep \
--deepep-mode auto \
--init-expert-location /path/to/expert_distribution_recorder_*.pt \
--enable-waterfill
```

PD 分离复现中，预填充服务端用 `normal` 模式，解码服务端用 `low_latency` 模式。两条命令都加相同的 `--init-expert-location` 参数：

```bash Command
# prefill
--moe-a2a-backend deepep \
--deepep-mode normal \
--init-expert-location /path/to/expert_distribution_recorder_*.pt \
--enable-waterfill

# decode
--moe-a2a-backend deepep \
--deepep-mode low_latency \
--init-expert-location /path/to/expert_distribution_recorder_*.pt \
--enable-waterfill
```

你还可以加 `--ep-num-redundant-experts` 与 `--eplb-algorithm` 自定义 EPLB 放置。

Waterfill 也支持 MegaMOE。用 `--moe-a2a-backend megamoe
--enable-waterfill` 保持 MegaMOE 后端，同时把 Waterfill 应用到融合的共享专家槽位。

**FP4 Indexer（实验性）**

除非设置 `--enable-deepseek-v4-fp4-indexer`，DeepSeek-V4 使用默认的 indexer 路径。启用该参数可在支持 DeepGEMM FP4 indexer 的 SM100 GPU 上使用实验性 FP4 C4 indexer。该路径面向解码密集的长上下文负载，可减少 indexer 缓存带宽占用。

```bash Command
# Please use the latest main branch for this feature.
sglang serve \
  --model-path deepseek-ai/DeepSeek-V4-Flash \
  --tp 4 \
  --moe-runner-backend flashinfer_mxfp4 \
  --enable-deepseek-v4-fp4-indexer
```

**NVFP4 混合检查点**

[`nvidia/DeepSeek-V4-Pro-NVFP4`](https://huggingface.co/nvidia/DeepSeek-V4-Pro-NVFP4) 与
[`nvidia/DeepSeek-V4-Flash-NVFP4`](https://huggingface.co/nvidia/DeepSeek-V4-Flash-NVFP4) 检查点
把 MoE 专家量化到 **NVFP4**，同时把注意力与稠密层保持在 **FP8**。
需要 `--moe-runner-backend flashinfer_trtllm_routed`（未指定时会自动选择）。

```bash Command
sglang serve \
  --model-path nvidia/DeepSeek-V4-Pro-NVFP4 \
  --tp 8
```

或

```bash Command
sglang serve \
  --model-path nvidia/DeepSeek-V4-Flash-NVFP4 \
  --tp 8
```

需要 Blackwell（SM100+）。该检查点中的 MTP 层保持 MXFP4 打包，并自动路由到 `Mxfp4FlashinferTrtllmMoEMethod` 路径。

<a id="hopper-note" />

**Hopper（H100 / H200）说明**

在 Hopper 上运行 DeepSeek-V4 有两条路可选：

- **原始 FP4 检查点** —— 命令生成器为 Hopper 单元格选用 W4A16 MoE kernel（Marlin）。该路径在 H100 与 H200 上均可工作，也是 H100 的唯一选择（无 FP8 路径）。它仅支持 TP；H200 上 Pro 变体可装入单个 8-GPU 节点，而 H100 Pro 需要 2 个节点（TP=16）。
- **转换后的 FP8 检查点**（仅 H100 与 H200）—— 预打包的 FP8 权重位于 [`sgl-project/DeepSeek-V4-Flash-FP8`](https://huggingface.co/sgl-project/DeepSeek-V4-Flash-FP8) 与 [`sgl-project/DeepSeek-V4-Pro-FP8`](https://huggingface.co/sgl-project/DeepSeek-V4-Pro-FP8)，可解锁 DP-attention + DeepEP 以及更丰富的并行度（例如 Pro 跨 2 节点的 TP=16）。

在这些 FP8 检查点上，还可以在 SM90 启用全 FP8 的 **MegaMoE** 路径，以提升长上下文/大解码吞吐——见下方配置技巧中的 **SM90 (Hopper) FP8 MegaMoE** 说明。

H200 上的 PD 分离方案可能需要 `docker run --privileged --ulimit memlock=-1`
（或 `--device /dev/infiniband:/dev/infiniband --cap-add IPC_LOCK`），让 mooncake
能发现 IB HCA；若未暴露 IB，mooncake 会静默回退到 TCP，在大检查点上可能导致 KV 传输损坏。

**RTX PRO 6000（SM120 / Blackwell 桌面）说明**

RTX PRO 6000（96 GB）仅用 FlashInfer MXFP4 MoE runner 运行 **Flash**。
V4-Pro 装不进 8× 96 GB；部署面板会置灰不支持的方案。
RTX PRO 6000 上**不支持** HiCache 与 MegaMoE。

**AMD（MI300X / MI355X）说明**

- **模型检查点** —— 为保证正确精度，FP4 模型使用原版 `deepseek-ai/DeepSeek-V4-{Flash,Pro}`，FP8 模型使用重新打包的 `sgl-project/DeepSeek-V4-{Flash,Pro}-FP8`。
- **支持的模型** —— **MI300X** 支持 FP8 的 DeepSeek-V4-Flash；**MI355X** 支持 FP4 与 FP8 的 DeepSeek-V4-Flash / Pro。所有方案均为单节点运行。
- **TP / DP 设置** —— TP=4 与 TP=8 均支持。低并发时推荐**仅 TP**；高并发时用 **TP + DP**，需要额外加 `--dp 8 --enable-dp-attention --enable-prefill-delayer --prefill-delayer-max-delay-ms 5000`。
- **MTP** —— 支持投机解码；加 `--speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`。
- **Kernel** —— 使用 Unified KV 注意力与 flydsl MoE。

**MegaMoE**

MegaMoE 把专家分派 + GEMM 融合进单个 kernel，提升 MoE 层的吞吐量。启用方法：用下方 Playground 里的 **MegaMoE** 芯片——Playground 会自动把 `--moe-a2a-backend deepep` 换成 `--moe-a2a-backend megamoe` 并添加相关环境变量。

暴露两个变体：
- **W4A8** —— 默认 MegaMoE kernel（FP4 权重、FP8 激活）。
- **W4A4** —— 增加 `SGLANG_OPT_DEEPGEMM_MEGA_MOE_USE_FP4_ACTS=1` 与 `SGLANG_OPT_DEEPGEMM_MEGA_MOE_USE_MXF4_KIND=1`，运行自定义 W4A4 kernel（FP4 激活）。吞吐更高，精度损失可忽略（Pro 上约 89.5 GPQA）。

注意：
- 上面的 W4A8 / W4A4 变体**仅限 Blackwell**（B200 / B300 / GB200 / GB300）。在 **Hopper（SM90，H100 / H200）** 上请改用下面描述的全 FP8 MegaMoE 路径。
- MegaMoE **只接入 Blackwell 上的 `high-throughput` 方案**（见 [sgl-project/sglang#26451](https://github.com/sgl-project/sglang/pull/26451)）。该芯片在 `low-latency` 与 `balanced` 上隐藏——切到 `high-throughput` 才会出现。
- 运行 MegaMoE 时不要手动设置 `--moe-runner-backend`。
- 按你的负载与显存使用调整 `SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK`。MegaMoE 处理更多 token 需要更多 HBM 空间（high-throughput 推荐 8320）。

**SM90（Hopper）FP8 MegaMoE（实验性）**

在 SM90（Hopper，H100 / H200）上，全 FP8 MegaMoE 路径把 MoE 路由到 DeepGEMM `mega_moe` runner，在 FP8 检查点上提升长上下文/大解码吞吐。与上面的 Blackwell W4A8 / W4A4 变体不同，这里的专家保持 **FP8** —— 保持 `SGLANG_DSV4_FP4_EXPERTS=0`。它需要一个带 SM90 FP8 MegaMoE 支持的 `sgl-deep-gemm` 构建。**该特性请使用最新镜像。**

用 `--moe-a2a-backend megamoe` 启用 MegaMoE 路径——或等价地设置 `SGLANG_OPT_USE_DEEPGEMM_MEGA_MOE=1`，它会自动配置相同的后端：

```bash Command
SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK=4096 \
SGLANG_DSV4_FP4_EXPERTS=0 \
sglang serve \
  --model-path sgl-project/DeepSeek-V4-Flash-FP8 \
  --tp 8 \
  --moe-a2a-backend megamoe \
  --chunked-prefill-size 4096
```

`SGLANG_OPT_DEEPGEMM_MEGA_MOE_NUM_MAX_TOKENS_PER_RANK` 限制 MegaMoE 路径每个 rank（即每张 GPU）处理的 token 数；只有不超过该上限的批会走 MegaMoE 路径。合适取值取决于你的并行/token 切分方式，更大的值会预留更多 HBM。

**GB300 PD 分离跨 pod MNNVL**

在某些通过 NVLink 做跨 pod KV 传输的 GB300 集群上，mooncake 可能报 `nvlink_transport.cpp:497 Requested address ... not found!`。若遇到，在预填充与解码两条 `sglang serve` 命令前加 `MC_FORCE_MNNVL=1 NCCL_MNNVL_ENABLE=1 NCCL_CUMEM_ENABLE=1`。

### 3.1 推理

启用 `deepseek-v4` 推理解析器（在[上方 Playground](#playground) 的 **Parsers** 卡片中切换 **Reasoning Parser**），即可把思考与最终答案分开为 `reasoning_content` 与 `content`。

```python Example

    ],

    extra_body={"chat_template_kwargs": {"thinking": True}},
    stream=True,
)

has_answer = False

for chunk in response:
    if not chunk.choices:

        if has_thinking and not has_answer:
            print("\n=============== Content =================", flush=True)

        print(delta.content, end="", flush=True)

print()
```

### 3.3 HiCache（分层 KV 缓存）

HiCache 支持多层级 KV 缓存卸载（GPU → CPU → 存储），显著扩展长上下文与多轮场景下的有效上下文容量。配合 UnifiedRadixTree，它能在所有层级间提供智能前缀缓存。

要启用 HiCache，打开[上方 Playground](#playground) 的 **HiCache** 卡片并打开 **Enable**：

- **L2（GPU + CPU）** —— 让 Storage 保持 `auto`（默认）。冷 KV 页只会溢到 CPU 固定内存。
- **L3（GPU + CPU + 存储）** —— 选一个存储后端（`file` / `mooncake` / `hf3fs` / `nixl`）；Playground 会输出规范的 `page_first_direct` 内存布局 + `direct` IO 后端 + `wait_complete` 预取策略，与 [HiCache 最佳实践方案](../../../docs/advanced_features/hicache_best_practices) 一致。

对于 AMD 设备：
- **L2（GPU + CPU）** —— 让 Storage 保持 `auto`（默认）。冷 KV 页只会溢到 CPU 固定内存。使用 `direct` IO 后端 + `page_first_direct` 或 `layer-first` 内存布局。
- **L3（GPU + CPU + 存储）** —— 选一个存储后端（`file`）；Playground 会输出规范的 `page_first_direct` 内存布局 + `direct` IO 后端 + `wait_complete` 预取策略，与 [HiCache 最佳实践方案](../../../docs/advanced_features/hicache_best_practices) 一致。

Write 策略旋钮默认为 `write_through`（上游默认）；当存储层较慢时，可切到 `write_back` / `write_through_selective`，用持久性换写入速度。

更多细节参见 [HiCache 文档](../../../docs/advanced_features/hicache)。

<Note>
💡 AI Infra 学习笔记：HiCache 是 KV 缓存的分层卸载——GPU 放不下就溢到 CPU 固定内存，再溢到存储（L2/L3），配合统一 Radix 树跨层做前缀缓存。本质是用"带宽换容量"：有效上下文容量大幅提升，但命中 CPU/存储层的请求会付出额外延迟。多轮对话与长上下文场景收益最大，需要按实际缓存命中率权衡层级配置。
</Note>

### 3.4 DSpark（投机解码） {#3-4-dspark-speculative-decoding}

Flash Official (0731) 在 `deepseek-ai/DeepSeek-V4-Flash-0731` 中捆绑了 DSpark 草稿头。因此目标与草稿权重来自同一个检查点：用 `--speculative-algorithm DSPARK` 启用 DSpark，不要单独设置 `--speculative-draft-model-path`。

与原始 Flash 和 Pro 检查点的 EAGLE 方案不同，该方案省略 `--speculative-num-steps`、`--speculative-eagle-topk` 与 `--speculative-num-draft-tokens`。SGLang 会从检查点读取 DSpark 形状。

已验证的 4×GB300 FP4 低延迟命令：

```bash Command
sglang serve \
  --trust-remote-code \
  --model-path deepseek-ai/DeepSeek-V4-Flash-0731 \
  --tp 4 \
  --moe-runner-backend flashinfer_mxfp4 \
  --speculative-algorithm DSPARK \
  --mem-fraction-static 0.90 \
  --chunked-prefill-size 4096 \
  --swa-full-tokens-ratio 0.1 \
  --host 0.0.0.0 \
  --port 30000
```

在该拓扑上保持 `--mem-fraction-static 0.90`，为批大小为 256 的验证图留足余量。首次冷启动可能耗时 10–15 分钟（FlashInfer 自动调优、SGLang 捕获草稿与验证图）；后续启动会复用缓存。该路径已在 SGLang v0.5.16 的 4×GB300 上端到端验证。

**调节提议的草稿 token 数。** `--speculative-dspark-block-size N` 让 DSpark 每步提议 `N` 个 token；目标模型验证一个 `N + 1` 的窗口。省略该参数时，SGLang 从检查点读取取值。当前 0731 检查点解析为 5 个提议 token，即已验证的默认值。用 [Playground](#playground) 里的 **DSpark Proposed Draft Tokens** 滑块在 1 到 5 之间扫描。

接受率高时更大的块能改善解码延迟，但也会增加验证工作量与图显存。从检查点默认值出发，在真实的提示词长度与并发分布下向下扫描。收益通常在短交互流量下最大，随着预填充占主导而收窄。请跟踪 P50/P99 TTFT 与 TPOT、总吞吐、接受长度、GPU 显存与停机率，而不要只看接受率。

对每个候选值，都要与去掉 `--speculative-algorithm DSPARK` 的相同方案对比。在 DSpark 与非投机两段之间重启服务端，保持请求语料、采样、并发与预热一致，并给每条 `bench_serving` 段各自的 `--flush-cache`。除非单独的剖析运行证明了覆盖的合理性，否则保持 `--speculative-draft-attention-backend` 不设置。

DSpark 目前需要 CUDA、`pp_size == 1`，且禁用 DP Attention。它不兼容当前 SGLang 发布版的 PD 分离部署；在选 prefill 或 decode 角色前先关掉 DSpark。因此 DP-Attention 与 MI355X Flash Official 方案只能目标模型单独运行。若更大的草稿块或并发导致图捕获 OOM，请降低 `--mem-fraction-static`、草稿块大小或配置的最大运行请求数，然后重跑性能与准确率两道门槛。
